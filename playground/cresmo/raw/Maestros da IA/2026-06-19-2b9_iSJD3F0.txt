O modelo de A sozinho sabe muita coisa, mas ele não toca o mundo real, não abre seus arquivos, não mexe no GitHub, não lê uma página e não fala com o seu slack. Para fazer algo de verdade, ele precisa se plugar em ferramentas externas. E existem três formas de fazer isso que você vai ouvir o tempo todo. CLI, API e MCP. São três siglas que confundem a grande maioria, mas hoje você vai entender essas três formas, como elas se conectam e como utilizá-las. E no fim uma sacada que

quase ninguém te conta. Elas não são rivais e muitas vezes uma utiliza a outra por baixo. E eu prometo que vou tentar ser menos técnica, mesmo que você nunca tenha aberto um terminal. Primeiro, entenda o problema que as três resolvem. Pensa no modelo de a como um cérebro genial, só que ele está trancado em uma sala. Ele leu milhões de livros,

só que não tem braços, não tem telefone e não vê seus dados. Mas para ser útil, nós precisamos dar a ele uma forma de estender a mão para fora dessa sala para que ele seja capaz de buscar informações, rodar uma ação ou chamar um serviço. E aí é que entram a CLI, a API e o MCP, que são três portas diferentes para isso. Cada uma tem o seu jeito, o seu custo e o seu momento certo para usar. Vamos uma por uma. A porta número

um é o CLI, Command Line Interface ou em português linha de comando. É o terminal, aquela tela preta que você digita ao invés de clicar. Através dele, o agente roda os mesmos comandos que um programador digitaria, como, por exemplo, ls para listar, catar um arquivo, grapar e curl para baixar uma página. E aqui está o pulo do gato. O modelo já conhece esses comandos de cor.

Ele foi treinado com milhões de exemplos. Stack overflow, manuais e documentação. É como pedir um bilhete para alguém que já fala português fluente. Você não precisa de dicionário, só escreve o agente simplesmente já sabe. Porta número dois, API.

Application programming interface. É o jeito clássico de um sistema acessar a função ou os dados de outro sistema. É um conjunto de regras dizendo como acessar uma informação ou um serviço. Pensa num balcão de atendimento. Você não entra na cozinha. Você faz o pedido

no formato certo e recebe a resposta. Você não precisa saber como funciona lá dentro. Exemplo, uma loja não cria um sistema de cartão do zero. Ela usa a API de pagamento de outra empresa, pede uma informação e recebe como recusado ou aprovado. O estilo mais comum é o REST, praticamente o padrão da web. Ele

conversa por http com quatro verbos simples: get para buscar, post para criar, para atualizar e delete para remover. Por exemplo, numa biblioteca get/books/123, pega os detalhes do livro 1 2 3 Post/Lans registra um empréstimo e a resposta vem em Jason com os dados organizados. E uma curiosidade é que a maioria dos LLMs comerciais é oferecida assim através de uma API REST. Ela manda um Jason com prompt e recebe um Jason com a resposta. Mas a API tem um problema com a IA. Uma particularidade é

que cada PI é única. Endereços, autenticações, parâmetros, tudo muda de serviço para serviço. Então, se você tiver cinco serviços diferentes, você vai precisar de cinco adaptadores diferentes. E as APIs não foram feitas pensando em a guarda isso, é aqui que entra o MCP. E antes de falarmos sobre MCP, eu quero te fazer um convite muito especial para entrar na comunidade Maestros da IA. Lá nós ensinamos tudo

Temos um curso completo de COD Code atualizado semana após semana, além de uma trilha com diversas ferramentas de a. Se você quiser saber mais, é só clicar no link na descrição desse vídeo. A porta número três e a mais nova que dá o que falar se chama MCP, Model Context Protocol, um padrão aberto criado pela Antropic, lançado no final de 2024. Ele padroniza como as aplicações entregam contexto e ferramentas para IA. A melhor metáfora,

e é oficial, é a seguinte: o MCP é como se fosse uma porta USBC para inteligência artificial. Pensa no seu computador que tem portas USBC. Você pluga nele HDs, carregadores, monitores e assim por diante. E não importa quem fabricou esses dispositivos, todos funcionam através de um mesmo padrão, de um mesmo plugin. O MCP é isso pra inteligência artificial. Em vez de cada

serviço ter um encaixe diferente, todos falam o mesmo idioma de conexão. Interessante. Mas como funciona isso por dentro? Tem um host que roda clientes. Cada cliente se conecta a servidores externos, formando assim uma relação cliente servidor. Cada servidor expõe

uma capacidade: banco de dados, um repositório, um e-mail. Na analogia, o laptop é o host e o USBC é o protocolo. E o monitor, o HD e o carregador são os servidores. E o MCP atende duas necessidades do agente. A primeira é dar o contexto através dos dados, que seriam documentos e registros. A segunda é dar

ferramentas através de ações, como fazer uma busca ou então chamar um serviço. O servidor anuncia o que ele chama de primitivas. Eu vou trazer três para que você conheça. A primeira delas são as tools. São as ações que a IA pode chamar. Por exemplo, um serviço de clima

expõe pegar previsão. Um de agenda expõe criar evento. O segundo são resources, ou seja, os recursos dados só paraa leitura, por exemplo, arquivos de texto ou o esquema de um banco. E por fim, os prompt templates, ou seja, os modelos de promptes prontos. Um ponto importante, nem todo servidor utiliza as três primitivas. Alguns focam apenas nas

tools, nas ferramentas. E aí vem a pergunta: se a API já funciona, por que inventar então o MCP? Porque existem dois recursos, dois superperes que a API comum não tem. O primeiro deles é a descoberta dinâmica. O agente faz a seguinte pergunta pro servidor: "Ei, o que você sabe fazer?" E o servidor

devolve a lista completa de tudo que oferece na hora. E se o servidor ganha uma função nova, o agente descobre sozinho, sem precisar reprogramar nada. Já na API Rest Comum não é bem assim. Se a API muda, o programador precisa ir lá e atualizar o cliente na mão. E o segundo super poder é a padronização.

Todo servidor MCP fala o mesmo protocolo. Você se lembra? Cinco APIs REST exigiam cinco adaptadores diferentes, mas cinco servidores MCP respondem às mesmas chamadas. Tem até uma frase para isso, para facilitar a recordação, que é a seguinte: construa uma única vez e integre com muitos. E agora vem uma sacada que muda tudo, a parte que quase ninguém menciona. MCP e

API não são inimigos, são camadas empilhadas uma sobre a outra. Quando você olha por dentro de muitos servidores MCP, sabe o que eles utilizam? APIs comuns. Na prática, um servidor MCP é muitas vezes um embrulho em volta de uma API existente. Ele recebe o pedido no formato MCP e traduz pra chamada da API nativa. Por exemplo,

o servidor MCP do GHub mostra para Eá ferramentas limpas, tipo listar, repositórios, mas por baixo ele vira uma requisição a API REST do GitHub. Pensa assim, a API é um motor que fica lá embaixo e o MCP é uma camada por cima com uma cara mais amigável paraa inteligência artificial. Isso já está em todo lugar. Arquivos, Google Maps, Docker, Spotify. OK. Mas e na hora de

fazer, qual delas eu escolho? CLI ou MCP? Um apresentador da IBM fez três testes reais. Teste um, simples, foi ler um arquivo e procurar uma palavra. No CLI, Cat e Grap, sem consultar nada. no

MCP, duas ferramentas de um servidor. No final, os dois funcionaram, mas o servidor anuncia 13 ferramentas e essas 13 fichas entram no contexto. Na prática, se for algo simples, tanto faz qual você vai utilizar. O teste dois foi o Git. No CLI, dois comandos resolvem.

Já no MCP, o servidor do GitHub traz 80 ferramentas. Todas as fichas entram no contexto, cerca de 55.000 tokens, usando uma ou duas. Mas como o token é dinheiro e é um espaço que some paraa ferramenta local, o MCP paga um imposto caro. Teste três, buscar uma página na web e fazer um resumo. O MCP usou um Fetcher, um

navegador sem telas. Uma chamada consumiu 250 tokens em 2 segundos. O CLI tentou com cur, mas a página era um next.jjs que só manda JavaScript. E o cur não roda JavaScript. E o agente

improvisou tanto que fez uma engenharia reversa do Framework só para ler a página. Passaram-se vários minutos, 2.000 tokens consumidos para obter o mesmo resultado. O veredito prático é: o CLI ganha quando o comando mapeia direto arquivos, scripts, texto e git e compõe com pipes encadeando comandos. O MCP não faz isso. O MCP ganha quando existe um

gap entre a ferramenta crua e o que você precisa. Além disso, ganha na autenticação. O servidor cuida dos tokens e logins por você e também ganha na governança de empresa. Acesso por usuário, sem senha compartilhada com auditoria. Agora vamos fechar o mapa das três portas que você aprendeu aqui. O

CLI é a língua nativa que o modelo já fala: direto, barato, para arquivo, gito. A API é o balcão clássico dos sistemas. É a camada crua por baixo de quase tudo, inclusive por baixo de muitos servidores MCP. E o MCP é a porta USBC da IA, padrão único, descoberta e governança. E muitas vezes ele usa a própria PI por baixo. E a resposta certa

não é escolher um, é usar as três no lugar certo. CLI quando comanda uma PEA, a PI como a base e MCP quando vale o custo. E um sinal de alerta divertido. Se um agente de A faz engenharia reversa de um framework para ler uma página, ele escolheu a ferramenta errada.
