  TypeScript is easy for models to write because it imposes few constraints. Those same missing constraints let models introduce data races that compile, run, and only fail intermittently. A thread safety bug in Rust does not compile. The compiler names the unsound type, explains why it cannot be sent between threads, and points the agent directly at the fix.
  
  Daniel Szoke, Rust SDK maintainer at Sentry, argues that optimizing for a language models can write easily is the wrong goal. The better optimization is a language whose compiler enforces correctness as a natural feedback loop. Every error an agent hits and resolves in a loop is a production bug that never ships. The Rust compiler is also faster than asking a review agent to find the same class of bugs and more reliable than hoping it does.

Então, como eu mencionei, Rust oferece muitas garantias de segurança, certo? Em

primeiro lugar, vale a pena mencionar que as normas de segurança são rigorosas. Não é possível contornar isso com qualquer tipo de conversão ou com uma conversão não verificada. A segurança contra valores nulos é outro ponto muito importante para quem vem de outras linguagens. Não existe um valor nulo universal. Se você deseja ter uma opção ou um tipo que possa estar vazio, precisa defini-lo explicitamente como um tipo de opção, e o compilador o forçará a sempre verificar se o valor existe antes de acessar o valor interno.

E a concorrência destemida, que eu acho realmente poderosa, significa basicamente que o compilador Rust verificará se você tem algum código multithread para garantir que todos os dados compartilhados entre as threads sejam tratados de forma thread-safe. E esta é apenas uma pequena lista. Há muitas outras coisas que o compilador Rust impõe, mas eu só quero dar a vocês um exemplo rápido de concorrência sem medo, porque acho que é realmente poderosa. Aqui está um pequeno exemplo de código. Basicamente, temos um contador aqui, que começará com o valor zero, e vamos criar 100 threads aqui.

E a cada vez, vamos pegar o contador e adicionar um a esse valor interno. Então, depois que todas essas threads terminarem, você esperaria que isso tivesse o valor de 100. Agora, há um problema aqui, que é o fato de que esses tipos são projetados para compartilhar dados mutáveis, mas apenas dentro de uma única thread. Eles não estão sincronizados para acesso seguro em ambientes multithread. Então, em uma linguagem como TypeScript, algo assim poderia compilar, poderia executar, e você só perceberia o problema quando, de vez em quando, obtivesse um valor diferente de 100, certo? E

pode ser, especialmente se for uma pequena parte de uma aplicação maior, que seja depurar onde essa condição de corrida de dados está ocorrendo. Mas em Rust, isso simplesmente não compila. Você receberá um erro de compilação, que dirá: "Erro: Não é possível enviar um Future entre threads com segurança. Este Future, ou seja, este pequeno bloco assíncrono aqui, não pode ser enviado. E 'send' significa que o envio entre threads é seguro, e este não é."

Portanto, este erro não é muito útil, mas se você rolar para baixo na mensagem de erro, encontrará uma explicação mais detalhada. E isso será realmente útil para o seu agente de IA, pois indica: "O valor aqui, este valor do contador que foi capturado, não pode ser enviado." Tem o tipo RC RefCell i32, e isso não é enviado." Então, se o seu agente de IA, ao compilar o seu projeto, receber esse erro de compilação, ele poderá imediatamente alterar isso para um tipo thread-safe , dos quais há muitos em Rust.
