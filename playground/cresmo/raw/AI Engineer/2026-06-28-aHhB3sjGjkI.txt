  Building an AI agent for a real team is not a prompt problem, it is a systems problem. In this session we walk through a practical, production-minded workflow for building an agent using a coding agent, and designing the codebase so that this loop stays reliable as complexity grows.
  
  The core pattern is two agents with different jobs. The coding agent is the builder: it writes and changes the agent’s codebase. The agent you are building is the product agent. It is the custom agent you ship for a client or for internal use.
  
  A key example is self-healing evals. We maintain an eval suite that exercises the product agent across representative tasks. When an eval fails, the builder agent runs the eval, inspects the failure artifacts, proposes a targeted fix to the correct layer (context, tool contract, or code), and opens a PR with a short report explaining what changed and what is still missing. If the agent cannot safely resolve the failure, it escalates by requesting specific human input and explaining exactly why it is blocked.

Então, uma vez que fornecemos contexto suficiente e damos ao agente de codificação a capacidade de testar suas alterações com alguns testes de regressão, tudo se torna muito, muito mais fácil para o agente de codificação.

E então, em alguns casos complexos, combinamos essa abordagem com o AutoAgent, e basicamente apontamos para o AutoAgent alguns dos clusters de falhas, e deixamos que o AutoAgent criasse alguns rascunhos de PRs para nós. Agora, é claro, tanto o AutoAgent quanto esse pipeline para aprimorar agentes com base em dados em tempo real são possíveis graças à Harness Engineering. Basicamente, a ideia central é que estamos aproveitando um conjunto de recursos para que nosso agente de codificação tenha ferramentas suficientemente poderosas para que possa alterar os códigos, validar suas próprias alterações, o que é extremamente importante, e então propor novas alterações caso as atualizações feitas não levem ao resultado desejado, certo? Resumindo muito rapidamente, a Engenharia de Acoplamento (Harness Engineering) consiste em construir o ambiente em torno do nosso agente de codificação para que ele possa funcionar de forma confiável. Então, estamos definindo todas as restrições, todas as tarefas, o ciclo de feedback, estamos dando a governança aos nossos agentes de codificação. E

estamos fazendo isso com algumas coisas, certo? Como já mencionamos. O primeiro é o ambiente de espectro. Assim, por exemplo, quando estamos tentando corrigir alguns modos de falha, cada modo de falha se torna uma especificação. Estamos criando uma especificação para o comportamento esperado do agente e, em seguida, implementando essa especificação.

Depois temos mecanismos de controle de qualidade, como a verificação de erros ( linting) em nossos testes unitários. Temos as nossas avaliações. Temos o LLM, revisão de código, então, um monte de coisas. Ah, tudo relacionado à engenharia de contexto, ou seja, fornecer o contexto correto ao nosso agente. E, claro, a observabilidade. Porque

precisamos saber o que está acontecendo, certo? Bem, se não sabemos o que está acontecendo quando enviamos o produto para a produção, basicamente estamos às cegas, certo? Portanto, queremos garantir que sabemos o que está acontecendo para que nosso agente de codificação possa corrigir quaisquer erros ou problemas assim que forem encontrados.
