Tailwind versão 4 e HTMLX. O Tailwind pinta a página, o HTML a faz mover. Você escreve HTML, o servidor envia HTML de volta, e essa troca constitui todo o aplicativo. Duas ressalvas antes de começarmos. A frase "zero JavaScript" contém um asterisco.

E existem três paredes onde essa pilha se interrompe. Primeiro o HTML, não é um framework e não há uma semana de aprendizado. São alguns atributos que você adiciona ao HTML simples. Você coloca hx get equals /messages em um botão. Quando alguém clica, o navegador solicita o URL ao servidor em segundo plano.

O servidor responde com um bloco de HTML. O HTML insere o código na página exatamente onde você o indicou. Sem necessidade de recarregar a página completamente, sem JSON para analisar, e toda a biblioteca tem cerca de 14 kilobytes. Para efeito de comparação, um aplicativo React típico utiliza de 2 a 400 kilobytes de JavaScript. Em seguida, o Tailwind versão 4 realiza o estilo.

Você descreve a aparência com nomes de classe curtos, posicionados ao lado da marcação à qual se aplicam. Aqui está o plano, o que cada ferramenta realmente faz, os resultados de reescritas reais, depois as três paredes e um veredicto direto no final. Então, o que o HTMLX realmente faz? Isso traz de volta a ideia sobre a qual a web nasceu. O servidor envia HTML simples com links e formulários, e o navegador apenas o renderiza .

Não existe uma segunda aplicação em JavaScript que dependa exclusivamente dela. A maior parte disso é composta por quatro atributos. hx get ou hx post indica para onde a requisição será enviada. O gatilho hx indica qual evento o dispara: um clique, uma tecla pressionada ou um envio. `hx target` define qual elemento será substituído, e `hx swap` define como o novo HTML será inserido.

Este último é mais flexível do que parece. Você pode substituir o conteúdo interno de um elemento , trocar o elemento inteiro ou adicionar novas linhas ao final de uma lista. A rolagem infinita se torna um único atributo e um pequeno código no servidor. Aqui está uma caixa de pesquisa real e funcional. HX post para /search, gatilho HX configurado para keyup com um atraso de 500 ms, para que espere até você parar de digitar, e alvo HX apontado para a lista de resultados.

Essa é toda a funcionalidade escrita na marcação. À medida que você digita, o servidor executa a consulta e retorna um bloco de linhas da tabela. O HTML os adiciona à lista. Você não escreveu uma chamada fetch. Não há estado a declarar nem indicador de carregamento a esquecer de desligar.

Carson Gross, criador do HTMX, chama isso de localidade de comportamento. Tudo o que um elemento faz está escrito nesse elemento. Você lê o que um botão envia e o que ele altera. Sem precisar vasculhar cinco arquivos diferentes. Compare isso com um aplicativo React moderno.

Antes mesmo de mexer em uma funcionalidade, você já está gerenciando seis camadas: um metaframework, uma biblioteca de estado, uma biblioteca de busca de dados, um pipeline de compilação, TypeScript e uma configuração de testes. O HTML remove a maior parte disso da interface e não se importa com o que está por trás dela. Qualquer coisa que retorne uma string funciona. Django, Rails, Go, Laravel, Flask, ASP.NET.

Se a sua linguagem consegue imprimir HTML, o front-end já está resolvido. Isso também não é algo marginal. Na pesquisa State of JS de 2025, divulgada em fevereiro deste ano, o React ainda lidera o uso com 83,6%, mas a satisfação com ele continua caindo, e o HTMLX está entre as ferramentas mais admiradas pelos desenvolvedores. E acaba de receber a sua maior atualização em anos. Em abril, foi lançado o HTML5 4.0,

reconstruído com base na moderna API fetch do navegador, substituindo o objeto de requisição de 20 anos que utilizava anteriormente. Essa única mudança possibilita o streaming nativo. A mesma ideia dos componentes de servidor React, porém em 14 KB. A versão 4 também incorpora duas coisas ao núcleo.

Idiomorfos, que comparam o HTML recebido com o que já está na tela e alteram apenas o que realmente mudou, e transições de visualização nativas, para que as páginas desapareçam e deslizem sem código adicional. Agora, até mesmo as falhas acontecem com elegância. Você para de alternar entre dois arquivos. Você para de dar nomes às coisas. Você para de percorrer uma folha de estilo, se perguntando se alguma regra antiga ainda está sendo usada em algum lugar. Todo o seu sistema de design cabe na marcação, sem necessidade de escrever media queries. A versão 4 repensou a configuração. O antigo arquivo de configuração JavaScript foi removido. Por baixo do capô, há um novo motor gráfico chamado Oxide, reescrito em Rust. A versão 3 utilizava Node e PostCSS. Este é um binário nativo e altera os números completamente. Isso é 182 vezes mais rápido. A construção deixa de ser algo que você espera . Você salva o arquivo e os estilos já estão na tela antes mesmo de seus olhos voltarem para o navegador. E ele só envia as classes que você realmente usou em qualquer parte do projeto. Uma página de produção completa gera cerca de 18 kilobytes de CSS após a compressão gzip, menor que a versão três que substituiu, e com mais recursos adicionais.

Ainda está se movendo rapidamente. A versão atual, 4.3, de maio, adicionou estilos de barra de rolagem de primeira classe e propriedades mais lógicas. E utiliza o CSS que o navegador executa nativamente. Consultas de contêiner, camadas em cascata, mistura de cores.

Eis o porquê de estes dois pertencerem um ao outro. Ambos estão contidos no seu HTML. O servidor renderiza as classes Tailwind e os atributos HTML no mesmo modelo, em uma única passagem. Não existe um aplicativo de interface separado para manter a sincronização. Assim, a arquitetura consiste em um único loop simples.

O navegador faz uma requisição, o servidor renderiza um fragmento HTML já estilizado com Tailwind. O HTML insere esse fragmento na página. Clique novamente e o loop será executado mais uma vez. Veja o que está faltando nesse ciclo. Sem roteador do lado do cliente , sem API JSON para projetar, versionar e documentar, sem armazenamento que mantenha uma segunda cópia dos seus dados.

O banco de dados permanece como a única fonte de verdade, do início ao fim. E se você já conhece o sistema interno, a curva de aprendizado é praticamente plana. Sem DOM virtual, sem reconciliação, sem ganchos para memorizar. Você depura o código usando a aba de rede do seu navegador, observando o tráfego HTML de ida e volta. Os recibos são válidos?

Considere uma reconstrução de concreto. Em novembro passado, um desenvolvedor reconstruiu um painel de administração React de produção exatamente com essa estrutura e mediu as duas extremidades. A reconstrução resultou em 890 linhas, um pacote de 14 kilobytes e um tempo de carregamento de 180 milissegundos .

Mesmo aplicativo, mesmas funcionalidades. Isso representa 72% menos carregamento de código, mais de 10 vezes mais rápido. Em um celular 3G com velocidade reduzida, a pontuação de desempenho do Lighthouse subiu de 34 para 94, a diferença entre uma experiência ruim e uma instantânea. Alinhe os pontos de partida . Significa que você não deve escrever nada. Você distribui uma pequena biblioteca estável que raramente é alterada, e o resto é HTML e CSS . Sem framework, sem etapa de compilação para seu próprio código. O que nos leva às três paredes, os locais reais onde você fecha este arquivo e abre o React .
