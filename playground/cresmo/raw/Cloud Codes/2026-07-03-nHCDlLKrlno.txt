Watch an AI agent try to use a website. It opens the page, takes a screenshot, and starts guessing. Which box is the search? Which button actually submits? It is squinting at pixels hoping it picked right. That is how almost every agent works today. It cannot really see your buttons. It sees a flat picture of pixels and just hopes it clicks the right one. Now watch the new way. The website simply hands the agent the controls. One clean, typed call, and the task is done. No squinting, no guessing, no second screenshot. This is WebMCP, the WebModelContext protocol. A way for any website to speak straight to AI agents built right into the browser itself. And the whole idea fits in three words. Publish tools, not pixels. Your site stops being a wall of buttons and agent has to decode and becomes a clean menu of actions it can simply call by name. It is the same model context protocol behind today's AI tools. But instead of a separate server, your page itself becomes a server right inside the tab. And it is dramatically leaner. Reading a page as a screenshot can burn 2000 tokens. A structured tool call costs around 50. Here is why it matters by 2027. If an agent can finish the job on your site but fumbles on your rivals, the agent sends every user straight to you, built by Google and Microsoft together through the W3C and shipping and Chrome right now. So let us take it apart. Start with the problem. For 30 years we have built the web for human eyes. Color, layout, icons, buttons you understand, the instant you see them. All of that meaning lives in the visuals and a person fills in the rest without even thinking about it. So how do agents browse it all today? Mostly by brute force, computer use models and automation frameworks that move a virtual mouse, read the raw page structure or snap screenshots and reason over them. It looks brilliant in a demo. In the real world it is fragile. Because that whole approach is a guessing loop, people call it actuation. Grab a screenshot, find a likely pixel, click it, grab another screenshot and check whether anything changed. The agent is reading your interface the way you would read a foreign newspaper through frosted glass. And it is painfully brittle. Move one button, rename a label, ship a small redesign and the agent's carefully learned script just shatters. It clicks where the button used to be, hits empty space and the whole task silently fails. No error, no recovery, it simply stops working. It is also slow and expensive. Every single step is a fresh, full page image and another round trip to the model. Multiply that across a checkout or a booking flow and you get something costly, sluggish, and almost impossible to trust in production. Web MCP flips the whole relationship around. Instead of the agent reverse engineering your screen, your website turns into a tiny tool server running right there in the browser tab. No extra back end to deploy, no new API to host. The page you already ship simply announces what it can do. If you have heard of MCP, this clicks fast. Regular MCP live server side, you stand up a separate service that speaks a protocol, connecting an AI to your back end. Web MCP takes that exact idea and moves it into the browser. No new server, no extra plumbing. The page in the tab is the provider. It runs in four clean steps. First, register. When the page loads, it tells the browser which tools it offers through a new object called navigator.modelcontext. Things like search flights, add to cart, or file a ticket. Each one declared upfront ready to be called. Second, discover. When an agent lands on the page, it does not stare at pixels anymore. It asks the browser one simple question, what can I do here? And gets back a structured list of every tool, each with a plain language description of exactly what it does. Third, invoke. The agent picks the right tool and calls it with typed parameters. The same way it would call any function, an origin, a destination, a date. No hunting for a button, no fragile click, no second screenshot, just to confirm something happened. Fourth, respond. Your own code runs the action and hands back structured data the model can read directly. The search results, a confirmation and order number. The model reads it, decides the next move, and the loop continues cleanly until the job is finished, and a tool is not some heavy new framework. It is just four small things, a name, a description in plain English, an input schema that defines the parameters, and an execute function that actually does the work. That is the entire contract. If you have ever defined a function, you already know this. There are two ways to add these tools, and the first is almost too easy. It is called the declarative API, and it works on plain HTML forms, no job is scripted all. You take a form you already have on the page, and you simply annotate it. You add two attributes, a tool name, and a tool description. That is genuinely it. The browser reads the form, turns its fields into a structured schema, and offers it to agents automatically. As one engineer put it, if your forms are already clean, you are 80% of the way there. And here's a neat touch. When an agent submits one of those forms, your code receives a flag, agent invoked, that tells you a machine did it, not a human. You can even respond with a structured result straight back to the model. One form quietly serves both a person and an agent. The second way is the imperative API, pure job script for richer dynamic tools. You call register tool, handed a schema and a function, and you can build anything, a live pricing lookup, a multi-step booking, a product filter. There is even a method to swap the whole tool set as your app changes state. And it is a real two-way conversation. Your tool can return a clean result or a clear descriptive error. Wrong date, sold out, missing field, the agent reads that error, understands what went wrong, and corrects itself, instead of blindly clicking the same broken thing again and again. A few habits make tools that agents love, name them with precise verbs, so create event is never confused with start event creation. Keep schema simple, accept a plain time string, do not make the model do math, validate strictly in your code, and return clear errors. Do that, and the agent rarely needs a second try. So why is this so much better? Because a tool is a contract, not a guess. You can redesign your entire page, move every button, change the whole layout overnight, and as long as the tool still exists, the agent keeps working perfectly. The interface and the capability are finally separated. It is also far faster and far cheaper. Around 50 tokens for a precise tool call, instead of 2000 for a screenshot, the model still has to decode. Analysts put it near a 90% cut in tokens, and close to 98% task accuracy. Faster, cheaper, and it actually finishes, and you stay in control. Everything is locked to your own origin. The browser acts as a gatekeeper, and the user is asked to confirm before anything sensitive runs, a payment, a delete, a booking. You decide exactly which actions you expose to agents, and absolutely nothing more. There is even a quiet bonus. The very same tools you publish for AI agents, also give a clean, reliable surface to screen readers and assistive technology. Build one structured layer, and you end up serving humans and machines at the very same time. What does this unlock in practice? Google's own previews point at three. Customer support, where an agent files a detailed ticket with every technical field already filled in. E-commerce, where it finds the right product, configures the options, and walks the checkout, and travel, where it searches, filters, and books the exact flight you wanted. And this is not one company's land grab. Google and Microsoft authored Web MCP together. Inside the W3C, the body that governs the open web. Engineers from both companies share the specification, which is exactly what you want from something that every site on Earth might one day adopt. It is also shipping right now, not someday. Web MCP is an early preview in Chrome 146 behind a flag you flip on for testing, with a stable release expected around the spring. The agentic web is being wired up quietly as we speak. And a small ecosystem is already forming around it, and inspector extension to see and test a page's tools, and open SDK built on the official protocol, and a community shipping live demos, from flight search to full checkout. The tooling is arriving fast. Now zoom out because the timing is the real story. Agentic browsing is exploding. The amount of agent traffic on the web has been doubling in a single month. More and more, the first visitor to your site is not a person at all. It is a model, acting on someone's behalf, which quietly splits the web into two jobs at once, pages that read well for people, and tools that run well for agents. The sites that win the next few years will not just have the prettiest interface. They will have the clearest set of actions an agent can actually call. And that is the case for the title. By 2027, an agent-ready site quietly closes the sale, books the trip, files the ticket, while the rest go invisible in the one moment that decides it. Being callable stops being a nice to have, and becomes simple table stakes. Now the honest part, this is not magic, and it is not finished. It is still a preview. There is no headless mode yet, and your interface has to stay in sync, whether a human or an agent is driving it. Real apps will need real work to expose clean, well-designed tools. And there is a classic chicken and egg catch. Sites wait for agents to matter, agents wait for sites to support them, and nobody has fully solved how an agent even discovers which sites offer tools. But with Google, Microsoft, and the W3C behind one shared standard that stalemate finally has a way to break. So here is the recap. Publish tools, not pixels, two ways to add them, declarative forms, and imperative JavaScript. Reliable because a tool is a contract. Fast and cheap because it skips the screenshots. Under your control, because you choose what to expose, and very soon simply expected. That is Web MCP, the quiet upgrade that turns every website into something agents can actually use.
