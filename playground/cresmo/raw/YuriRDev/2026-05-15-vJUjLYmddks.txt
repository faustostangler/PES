Depois que meu usuário autentica, como que o sistema lembra quem que ele é nas próximas requisições? O HTTP é um protocolo sem estado. Cada requisição é independente. O servidor não guarda o

Se o heads cair, tudo cai. A alternativa foram os tokens stateless, como o JWT. Em vez de guardar a sessão no servidor, toda a informação fica no próprio token e o token fica pro cliente. Ele é composto

por um header, payload e a signature, todos separados por ponto. O header fica definido o tipo de token e o algoritmo de assinatura, tipo HS256. No estão os dados, o user ID, as permissões, quando o token inspira e tanto o payload quanto o header são codificados em base 64, não criptografados. Qualquer um pode ler e mudar o conteúdo, mas o que garante a integridade é a assinatura. Se alguém alterar o payload, a assinatura fica invalidada e o servidor rejeita o token.

No login, o servidor gera e assina o JWT e envia pro cliente. E nas próximas requisições, o cliente envia o token no header e o servidor só verifica a assinatura sem precisar consultar banco de dados e isso escala muito melhor. Qualquer servidor com a chave de verificação pode validar um JWT. Mas surge um outro problema. Como o JWT também é stateless, como você invalida um token antes dele inspirar? Se o

usuário fizer logout ou tiver a conta comprometida, o token continua válido até inspirar. A solução é trabalhar com tokens de curta duração, tipo um Access token que expira em minutos, mas aí o usuário teria que fazer login a cada 15 minutos, o que seria insuportável. Então vamos usar também o refresh token. A ideia é que o Access token vai ter uma curta duração de 15 minutos, 1 hora e é usado em cada requisição. E o refresh token vai ter uma duração maior de dias ou até semanas. Quando o Access token

inspira, o cliente envia o refresh token para um end point específico, o servidor valida e emite um novo access token. E também o refresh token pode ser invalidado. Se o usuário fizer logout a conta for comprometida, o servidor marca aquele refresh token revogado e na próxima tentativa de renovação, o servidor recusa e o usuário tem que autenticar de novo. É o melhor dos dois mundos. São requisições rápidas e statless com access tokens curtos e controle de revogação centralizado com refresh tokens.
