O Kubernetes é uma plataforma de orquestração de contêineres de código aberto que automatiza a implantação, o dimensionamento e o gerenciamento de aplicativos em contêineres. No desenvolvimento de software moderno, os aplicativos são frequentemente empacotados em unidades portáteis e leves chamadas contêineres. Embora executar um único contêiner seja simples, gerenciar centenas ou milhares deles em uma frota de máquinas apresenta desafios significativos. O Kubernetes

aborda esses desafios fornecendo uma estrutura robusta para executar sistemas distribuídos de forma resiliente. Os principais benefícios do Kubernetes incluem a autorrecuperação, que reinicia automaticamente os contêineres com falha e os reprograma em nós íntegros; o escalonamento automático, que permite que os aplicativos sejam dimensionados com base no uso de recursos; e as implantações sem tempo de inatividade, essenciais para implementar atualizações sem interromper o serviço. O princípio fundamental que sustenta o Kubernetes é seu modelo declarativo. Em vez de emitir uma série de comandos imperativos como "execute este contêiner" ou "pare aquele", um administrador define o estado desejado do sistema em arquivos de manifesto YAML. Esses arquivos descrevem quais aplicativos devem estar em execução, quantas réplicas eles devem ter, quais políticas de rede devem ser aplicadas e assim por diante. Uma vez que esses manifestos são aplicados ao cluster, os controladores do Kubernetes trabalham continuamente em um loop de controle para observar o estado real do cluster e fazer alterações para reconciliá-lo com o estado desejado. Se um pod falhar, o

controlador percebe a discrepância entre a contagem de réplicas desejada e a contagem real e cria uma nova. Este modelo é a base dos recursos de autorrecuperação e automação do Kubernetes. Antes de se aprofundar em tarefas administrativas avançadas, é importante ter um sólido conhecimento da arquitetura do Kubernetes e de seus componentes principais . Esta seção aborda a estrutura conceitual de um cluster Kubernetes e fornece um guia passo a passo para configurar um ambiente de prática local que reproduza as ferramentas e configurações que você encontrará no exame CKA. Um cluster Kubernetes segue uma arquitetura mestre-escravo ou, mais precisamente, uma arquitetura de nó de trabalho com plano de controle. O plano de controle atua como o cérebro, tomando decisões globais e gerenciando o estado do cluster, enquanto os nós de trabalho são os músculos que executam as cargas de trabalho reais do aplicativo. O plano de controle é o conjunto de componentes responsáveis ​​pela orquestração dos contêineres e pela manutenção do estado desejado do cluster. Ele pode ser

executado em uma única máquina ou replicado em várias máquinas para alta disponibilidade. O servidor da API do cubo é o hub central e a interface do plano de controle. Toda a comunicação de e para o cluster passa pelo servidor de API. Ele expõe uma API do Kubernetes, valida e processa todas as solicitações da API e coordena todos os processos entre o plano de controle e os componentes do nó de trabalho . ETCD é a única fonte de verdade do cluster. Trata-se de um armazenamento de

chave-valor distribuído, consistente e de alta disponibilidade, onde todos os dados do cluster, seu estado de configuração e metadados são armazenados para garantir segurança e consistência. O acesso direto ao ECTD é restrito. Todas as interações devem ser feitas através do servidor da API do cubo. O cubeuler atua como o intermediário do cluster. Ele monitora pods recém-criados que ainda não possuem um nó atribuído. Para cada pod desse tipo, o

Theuler encontra o melhor nó para sua execução com base em um conjunto complexo de fatores, incluindo requisitos de recursos, restrições de hardware, regras de afinidade e antiafinidade e localidade de dados. O gerenciador do controlador do cubo é o piloto automático do cluster. Ele executa vários processos de controlador em segundo plano. Cada controlador é um circuito de controle que monitora o estado compartilhado do cluster por meio do servidor da API do cubo e trabalha para mover o estado atual em direção ao estado desejado. Exemplos incluem o controlador de nós, que lida com falhas de nós, e o controlador de replicação, que mantém o número correto de pods. Os nós de trabalho

são as máquinas onde seus aplicativos são executados. Eles são gerenciados pelo plano de controle e contêm todos os serviços necessários para executar contêineres. O cublet é o agente de nó primário que é executado em cada nó de trabalho. Ele se comunica com o servidor da API do cubo para receber instruções e reportar o status do nó e seus contêineres. Sua principal função é garantir que os contêineres descritos nas especificações do pod estejam em execução e funcionando corretamente. Ele gerencia

todo o ciclo de vida dos contêineres em seu nó. O Cube Proxy é um proxy de rede que roda em cada nó e é parte fundamental do conceito de serviço do Kubernetes. Ele mantém regras de rede no nó, permitindo a comunicação de rede com seus pods tanto de dentro quanto de fora do cluster. Ele pode usar vários modos para direcionar o tráfego destinado ao IP virtual de um serviço para o pod de backend correto. Por fim, o ambiente de execução do contêiner é o software responsável por executar os contêineres. O

Kubernetes suporta vários ambientes de execução de contêineres, como containerd e CRIO. O cublet se comunica com o ambiente de execução do contêiner usando a interface de ambiente de execução do contêiner ou CRI. Para gerenciar operações de contêineres, como baixar imagens e iniciar e parar contêineres, os objetos do Kubernetes são entidades persistentes no sistema Kubernetes. Ao criar um objeto, você está dizendo ao sistema Kubernetes como deseja que seja a carga de trabalho do seu cluster. Este é o estado desejado do seu cluster. Os pods

são a unidade implantável mais pequena e fundamental no Kubernetes. Eles representam uma única instância de um processo em execução no seu cluster. Um pod encapsula um ou mais contêineres fortemente acoplados que compartilham recursos de armazenamento, um endereço IP de rede exclusivo e opções que regem como o contêiner deve ser executado. Embora uma cápsula possa conter vários recipientes, o padrão mais comum é um recipiente por cápsula. Conjuntos de réplicas e implantações. O

objetivo de um conjunto de réplicas é manter um conjunto estável de pods de réplica em execução a qualquer momento. Isso garante a disponibilidade de uma especificação de um número determinado de cápsulas idênticas. Um deployment é um objeto de nível superior que gerencia conjuntos de réplicas e fornece atualizações declarativas aos pods. Você descreve um estado desejado em uma implantação e o controlador de implantação altera o estado atual para o estado desejado a uma taxa controlada. Os deployments são a maneira padrão e recomendada de gerenciar aplicações sem estado em serviços do Kubernetes. Como os pods são

efêmeros e seus endereços IP podem mudar, um serviço fornece um ponto de extremidade estável para acessar um conjunto lógico de pods. Um serviço atua como uma abstração, definindo uma política para acessar os pods e fornecendo um endereço IP virtual estável ou o IP do cluster e um nome DNS. Todo o tráfego enviado para o serviço é automaticamente balanceado para os pods de backend apropriados. Os espaços de nomes fornecem um mecanismo para isolar grupos de recursos dentro de um único cluster. São uma forma de dividir os recursos do cluster entre vários usuários ou equipes. Os nomes dos recursos precisam ser

únicos dentro de um espaço de nomes, mas não entre espaços de nomes diferentes. Isso permite que diferentes equipes usem os mesmos nomes de recursos sem conflito. Kubernetes foi projetado para ser extensível. Sua funcionalidade principal pode ser aprimorada por meio de interfaces padronizadas e pela adição de tipos de recursos personalizados. A CRI, ou interface de tempo de execução de contêiner, é uma interface plug-in que permite ao cublet usar uma ampla variedade de tempos de execução de contêiner sem a necessidade de recompilar o Kubernetes. A CNI, ou interface de rede de contêiner, é uma especificação para configurar interfaces de rede para contêineres Linux. Permite que diferentes soluções de rede se integrem ao Kubernetes para fornecer rede para os pods. A CSI, ou

interface de armazenamento de contêineres, é um padrão para expor sistemas de armazenamento a cargas de trabalho conteinerizadas. Isso permite que fornecedores de armazenamento de terceiros desenvolvam plugins que funcionem em diferentes orquestradores de contêineres, incluindo o Kubernetes, sem precisar adicionar seu código ao repositório principal do Kubernetes. Uma definição de recurso personalizada, ou CRD, é um recurso poderoso que permite estender a API do Kubernetes com seus próprios tipos de recursos personalizados. Se você deseja gerenciar um novo tipo de objeto, como um banco de dados, pode criar um CRD para ele e interagir com ele usando o controlador de cubo, assim como faria com um recurso integrado, como um pod. As solicitações representam a quantidade de CPU e memória garantida para um contêiner. O Kubernetes usa o valor da solicitação para decidir em qual nó colocar o pod. Os limites representam a

quantidade máxima de memória da CPU que um contêiner pode usar. O cubículo impõe esses limites. Se um contêiner exceder seu limite de CPU, seu desempenho será limitado. Se exceder o limite de memória, será encerrado com um erro de OOM (Out of Memory). A relação entre solicitações de recursos, agendamento e escalonamento automático é um sistema crucial que precisa ser compreendido. A falha em configurar as solicitações

impede o funcionamento do HPA. Definir um número excessivo de solicitações pode fazer com que os pods fiquem presos em um estado pendente se nenhum nó individual tiver recursos alocáveis ​​suficientes para atender à solicitação. Definir limites muito baixos pode fazer com que os aplicativos sejam encerrados inesperadamente sob carga. Embora muitas aplicações conteinerizadas sejam sem estado, aplicações com estado, como bancos de dados, exigem armazenamento que persista além do ciclo de vida de um único pod. O Kubernetes fornece uma estrutura de armazenamento poderosa e abstrata, construída em torno de volumes persistentes, solicitações de volumes persistentes e classes de armazenamento. É importante distinguir entre os diferentes conceitos de volume no Kubernetes. Um volume é um diretório

que contém dados acessíveis aos contêineres em um pod. O ciclo de vida de um volume está ligado ao ciclo de vida da cápsula que o contém. Quando o pod deixa de existir, o volume é destruído e seus dados são perdidos. Isso é adequado para dados efêmeros. Um volume persistente, ou PV, é uma unidade de armazenamento no cluster que foi provisionada por um administrador ou provisionada dinamicamente usando uma classe de armazenamento. É um recurso

do cluster, assim como uma CPU ou memória. A principal característica de um sistema fotovoltaico é que seu ciclo de vida é independente de qualquer célula individual que o utilize. Quando um pod é excluído, os dados no PV são mantidos. Uma solicitação de volume persistente, ou PVC, é uma solicitação de armazenamento feita por um usuário. Um desenvolvedor cria um PVC especificando o tamanho e o modo de acesso necessários, sem precisar conhecer os detalhes da infraestrutura de armazenamento subjacente. O

PVC funciona como uma garantia sobre um recurso fotovoltaico. Quando um usuário cria um PVC (Platinum Volume Controller), o plano de controle do Kubernetes procura um PV que possa atender aos requisitos das declarações. Se um PV adequado for encontrado, o plano de controle vincula o PVC a esse PV. Trata-se de um mapeamento um-para-um . Uma vez vinculado, nenhum outro PVC pode reivindicar esse PV. Um pod pode então solicitar

o armazenamento fazendo referência ao PVC em sua definição de volume. Ao definir PVs e PVCs, duas das especificações mais importantes são o modo de acesso e a política de recuperação. Os modos de acesso definem como um volume pode ser montado pelos nós do cluster. O modo de acesso escolhido deve ser compatível com o provedor de armazenamento subjacente . Os modos de acesso primários são leitura e gravação uma única vez, ou RWO, o que significa que o volume pode ser montado como leitura e gravação por um único nó. Este é o

modo de acesso mais comum e é compatível com a maioria dos tipos de volume. Mini ou ROX somente leitura, o que significa que o volume pode ser montado como readon por vários nós simultaneamente. O modo de leitura e gravação "RWX" significa que o volume pode ser montado como leitura e gravação por vários nós simultaneamente. Isso é suportado por sistemas de arquivos de rede como NFS ou SEF FS e pelo modelo RWOP (Read Write Once Pod), que é um modelo mais recente que restringe o acesso ao volume a um único pod. Esta é a opção mais restritiva e segura . A política de recuperação de um

volume persistente informa ao cluster o que fazer com o volume depois que sua reivindicação de volume persistente vinculada for excluída. Uma política de retenção significa que, quando o PVC é excluído, o PV permanece. O volume, seus dados e o recurso de armazenamento subjacente não são excluídos. O administrador do cluster deve limpar manualmente o volume e seus dados. Essa é a política mais segura para dados de produção. Uma política de exclusão significa que, quando

o PVC é excluído, o PV e o ativo de armazenamento externo associado são excluídos automaticamente. Essa é geralmente a configuração padrão para volumes provisionados dinamicamente . Uma política de reciclagem realiza uma verificação básica do volume e o disponibiliza novamente para uma nova solicitação. Essa política não é mais recomendada devido a preocupações com a segurança e foi substituída pelo provisionamento dinâmico. OK.

A resolução de problemas é o domínio com maior peso no exame CKA, refletindo sua importância no trabalho diário de um administrador de Kubernetes. Uma abordagem sistemática e lógica é fundamental para diagnosticar e resolver problemas de forma eficiente em um sistema distribuído complexo como o Kubernetes. Uma abordagem caótica para a resolução de problemas leva à perda de tempo e a possíveis diagnósticos incorretos.

Uma metodologia estruturada é essencial, especialmente em um ambiente de exame com tempo determinado. A abordagem recomendada envolve cinco etapas. Primeiro, identifique o problema. Defina claramente o que não está funcionando. Algum pod está apresentando falhas? O serviço está inacessível?

O cluster não está respondendo? Comece com uma verificação de alta prioridade, como obter pods do controlador de cubo . Em segundo lugar, reúna informações. Coletar registros, eventos e definições de recursos para entender o contexto da falha. O comando `describe` do controlador de cubo é uma das ferramentas mais poderosas para esta etapa. Terceiro,

analise os dados. Analise as informações coletadas para formular uma hipótese sobre a causa raiz. Procure por mensagens de erro, condições de status e eventos relevantes. Quarto, implemente uma solução. Aplique uma correção com base na sua hipótese. Isso pode

envolver a edição de um manifesto YAML, a correção de um comando ou a reinicialização de um componente. E em quinto lugar, verifique a solução. Confirme se a correção resolveu o problema e não introduziu nenhum novo problema. Na resolução de problemas, costuma ser eficaz trabalhar da camada de aplicação para a camada de infraestrutura. Componentes de pod, serviço, nó e cluster. As

falhas de pods são os problemas mais comuns que um administrador enfrentará. Os pods podem não iniciar ou apresentar falhas durante a execução por diversos motivos. O estado de um pod fornece a primeira pista sobre o que pode estar errado. O status "pendente" significa que o pod foi aceito pelo cluster, mas um ou mais de seus contêineres ainda não foram criados. Isso pode ocorrer porque está aguardando agendamento ou está baixando imagens. A criação de um contêiner

significa que o pod foi agendado para um nó, mas o ambiente de execução do contêiner está em processo de inicialização do contêiner. A mensagem "Image pull back off" ou "error image pull" significa que o Cublet não conseguiu extrair a imagem do contêiner do registro. "Crash loop back off" significa que um contêiner no pod foi iniciado, mas sua execução apresentou um erro. O Cublet tenta reiniciar repetidamente, mas continua travando. Um status de erro significa que o pod falhou e a fase não foi concluída com sucesso, enquanto "om killed" significa que o contêiner foi encerrado porque excedeu seu limite de memória. O motivo mais comum para

um pod ficar preso no estado pendente é uma falha de agendamento. Isso pode ocorrer devido a recursos insuficientes, falha nas regras de afinidade/antiafinidade de nós, o nó estar corrompido e o pod não possuir tolerância ou uma solicitação de volume persistente não vinculada . O comando `cube controller describe pod` é a ferramenta mais importante aqui. A seção de eventos na parte inferior fornecerá um motivo claro, como por exemplo, "0/3 nós disponíveis, três CPUs insuficientes". Se a causa estiver relacionada a recursos, verifique a capacidade do nó com o controlador de cubo "descrever nó". A

causa geralmente é um nome ou tag de imagem incorretos no manifesto do pod, um erro de autenticação com um registro privado ou o registro estar inacessível. A melhor maneira de depurar o problema é usar novamente o comando `cube controller describe pod`. Os eventos mostrarão um evento com falha, com a mensagem "falha ao obter a imagem" e um erro específico. Este costuma ser o problema mais complexo, pois indica uma falha no aplicativo ou em sua configuração. A causa provavelmente é um erro no código do aplicativo ou uma configuração incorreta, uma falha na sonda de luminosidade ou permissões de arquivo incorretas. O

passo mais crítico aqui é verificar os registros. Os registros quase sempre conterão a mensagem de erro ou o rastreamento da pilha que revela a causa raiz. Você também pode verificar a descrição do pod para procurar pistas e o código de saída do contêiner. Se o contêiner iniciar, mas falhar muito rapidamente para que você possa obter os registros, talvez seja necessário modificar seu comando para mantê-lo ativo para depuração. Por exemplo, altere o comando para sleep 3600 e, em seguida, use cubecontroller exec para obter um shell dentro do sistema. O

Kubernetes fornece outro mecanismo para que os contêineres relatem eventos fatais. Mensagens de encerramento. Um contêiner pode escrever uma mensagem breve em um arquivo e o Kubernetes exibirá essa mensagem no último estado. Campo de mensagem de término do status do contêiner, que é visível na saída do comando `cube control describe pod`. Isso pode ser útil para fornecer um resumo conciso de uma falha quando os registros completos são muito extensos.

Se as aplicações estiverem apresentando falhas em todo o cluster, o problema pode estar nos nós ou no próprio plano de controle. Os nós podem estar em vários estados. Os estados problemáticos mais comuns são "não pronto" e " agendamento desativado". Um nó não pronto significa que o cublet no nó não está reportando um estado saudável para o plano de controle. Isso pode ocorrer porque o processo do Cublet não está em execução. O nó

possui uma partição de rede que o impede de alcançar o servidor da API, ou a máquina subjacente está inativa. O primeiro passo para depurar o problema é acessar o nó afetado via SSH e verificar o status do serviço Cublet. Se não estiver em execução, tente iniciá-lo. Você também pode examinar os registros do Cublet em busca de erros. Um nó com agendamento desativado significa que o agendador não colocará novos pods nele. A causa

geralmente é que um administrador isola manualmente o nó com frequência para manutenção. A solução é usar o comando uncordone do controlador de cubo em um cluster com o Cube ADM instalado. Os componentes do plano de controle são executados como pods estáticos. Os seus manifestos YAML estão localizados em etc/ubernetes/manifests no nó do plano de controle. O cublet nesse nó é responsável por garantir que esses pods estejam em execução. Falha no serviço de API

. Se o servidor da API estiver inativo, os comandos do controlador do cubo falharão com um erro de conexão recusada. Para depurar o acesso SSH ao nó do plano de controle, verifique se o contêiner do servidor da API do Cube está em execução usando a interface de linha de comando do ambiente de execução do contêiner . Verifique os registros. Por fim, inspecione o arquivo de manifesto em busca de erros de sintaxe ou parâmetros incorretos.

Falha no agendador ou no gerenciador de controladores. Os sintomas incluem novos pods permanecendo pendentes indefinidamente em caso de falha do agendador ou implantações que não criam novos pods devido a uma falha do gerenciador de controladores. O processo de depuração é o mesmo que para o servidor de API. Acesse o nó do plano de controle via SSH e inspecione o pod estático correspondente e seus logs. Os problemas de conectividade de serviço podem ser complexos. Uma verificação sistemática é a melhor

abordagem. Suponha que você tenha um pod cliente que não consegue se conectar a um serviço. Primeiro, verifique a resolução de DNS. A partir do pod do cliente, tente resolver o nome do serviço com uma pesquisa NS. Se isso falhar, o problema provavelmente está no núcleo do DNS. Em segundo lugar,

verifique o serviço e os endpoints. Verifique se o serviço existe e se selecionou os pods de back-end corretos usando o comando `cubecontroller describe service`. Se a lista de endpoints estiver vazia, significa que o seletor de serviços não corresponde aos rótulos de nenhum pod em execução. Corrija as etiquetas nos pods ou no seletor do serviço. Terceiro, verifique a conectividade do pod. Tente conectar-se diretamente ao

endereço IP de um pod de back-end a partir do pod cliente. Se isso falhar, o problema está em um nível inferior, possivelmente relacionado ao plugin CNI ou a uma política de rede. E, por fim, verifique as políticas de rede. Se as políticas de rede estiverem em vigor, elas podem estar bloqueando o tráfego. Exclua temporariamente quaisquer políticas relevantes para verificar se a conectividade é restaurada. Caso isso ocorra, a

política precisa ser ajustada para permitir o tráfego necessário. Compreender o consumo de recursos é importante para diagnosticar problemas de desempenho e falhas de agendamento. O comando principal de controle do cubo, que depende do servidor de métricas, é a ferramenta essencial para isso. Você pode verificar o uso de recursos do nó para obter uma visão geral da utilização de CPU e memória de cada nó. Isso ajuda a identificar nós que estão sob pressão, o que pode explicar por que os pods estão sendo limitados ou removidos. Você também pode detalhar a análise

para visualizar o uso de recursos de pods individuais. Isso é extremamente valioso para diagnosticar erros de "om killed", por exemplo, comparando o uso com o limite de memória do pod, e para ajustar o HPA e os alvos do HPA observando o uso típico da CPU sob carga.
