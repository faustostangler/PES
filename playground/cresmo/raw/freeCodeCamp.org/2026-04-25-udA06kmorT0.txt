Na minha experiência, o desenvolvimento orientado a testes não é muito eficaz para testar resultados negativos, certo? É tipo, sabe, escrever o código, escrever o teste, garantir que o teste diga que falhou, escrever o código, o teste passa, beleza, vamos para a próxima coisa, certo? Não, não, não, não. Teste aprovado, ótimo. Ora, o que poderia dar errado, não é mesmo? Quais são os outros

cenários? Como se escrevem testes para isso? Esse tipo de coisa. O TDD não é muito bom em incentivar as pessoas nessa direção. O segundo problema com o TDD é que, na minha opinião, ele é muito localizado. Quando escrevo meus

testes TDD, quando escrevo meus testes localizados, estou escrevendo testes para verificar se o código faz o que eu acho que ele deveria fazer, certo? E se o meu entendimento sobre o que o código deve fazer for diferente do que outra pessoa no projeto acha que o código deve fazer, e nossos códigos estiverem interagindo entre si, então o conjunto de elementos que se comunicam de ponta a ponta não vai funcionar. Mas não é possível fazermos isso individualmente. Para que isso aconteça, é preciso realizar testes de ponta a ponta.
