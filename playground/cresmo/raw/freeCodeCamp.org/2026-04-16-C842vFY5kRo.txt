Então, vamos começar com o primeiro passo e configurar um servidor único . Imagine que estamos configurando um sistema para uma pequena base de usuários. Isso significa

que tudo funciona em um único servidor: o aplicativo web, o banco de dados, o cache e também os demais componentes. E essa configuração nos permite visualizar o funcionamento básico sem complexidade adicional. Agora, vamos analisar como essa configuração de servidor único lida com as solicitações do usuário. Temos alguns usuários que estão tentando acessar nosso site ou nossa API no servidor. Eles podem acessar nosso servidor tanto pelo navegador da web quanto por um aplicativo móvel . Por outro

lado, temos o nosso servidor, que contém os arquivos necessários para serem disponibilizados aos navegadores web, bem como os endpoints da API necessários para o aplicativo móvel. E está hospedado neste endereço IP de exemplo . Inicialmente, nossos usuários não possuem esse endereço IP, mas sim o domínio que estão tentando acessar. Vamos supor que seja app.demo.com.

Portanto, se eles simplesmente digitarem esse nome de domínio e pressionarem Enter, o navegador da web deles, por exemplo, entrará em contato com o DNS, que significa sistema de nomes de domínio. Este é um provedor que mapeia os domínios para os endereços IP. E no nosso caso, digamos que o nosso nome de domínio esteja mapeado para o endereço IP, que é o endereço IP do servidor que temos. Assim, esse provedor de DNS enviará o endereço IP de volta para o navegador da web ou para o aplicativo móvel, para nossos clientes. E esse endereço IP é o endereço IP do nosso servidor, então agora eles têm a localização de onde estão tentando enviar as solicitações. Assim, com esse

endereço IP em mãos, o dispositivo do usuário envia uma solicitação HTTP ao nosso servidor pedindo dados específicos. Em seguida, nosso servidor processa essa solicitação e envia os dados solicitados. Isso pode ser uma página HTML para um navegador ou uma resposta JSON para o aplicativo, dependendo do tipo de solicitação. Nessa configuração, o tráfego geralmente se origina de duas fontes principais. O primeiro grupo são os aplicativos web, e o segundo são os aplicativos móveis que estão tentando acessar nosso servidor. Para os nossos usuários da web,

o servidor lida com a lógica de negócios, o armazenamento de dados e também com a apresentação, utilizando HTML, CSS e JavaScript. E para usuários de dispositivos móveis, a comunicação normalmente ocorre via HTTP. Esses aplicativos móveis solicitam dados do servidor usando chamadas de API, e o JSON é frequentemente usado para as respostas porque é leve e fácil de interpretar para dispositivos móveis. Aqui está um exemplo de solicitação de API que podemos receber para o nosso servidor. Pode ser uma solicitação GET para o nosso domínio/produtos/o ID desse produto. E para este

endpoint, precisamos recuperar os detalhes de um produto. E aqui está um exemplo de resposta que poderíamos enviar ao cliente. Esta é uma resposta JSON que contém o ID do produto. Contém o nome do produto, uma descrição, o preço e outros metadados úteis para o cliente. E então, isso será usado pelo aplicativo móvel ou pelo navegador da web para exibir este produto na tela. E, à medida que avançamos, nosso objetivo

será identificar áreas onde um único servidor pode não ser suficiente para atender à demanda do usuário. Por enquanto, essa configuração é ideal para bases de usuários pequenas, mas pode apresentar dificuldades sob tráfego intenso. Em seguida, exploraremos maneiras de dimensionar cada parte do sistema para suportar mais usuários de forma eficaz. Uma das principais conclusões que podemos tirar disso é que precisamos começar pequeno. Precisamos começar com uma configuração simples de servidor único para entender os componentes essenciais da arquitetura do sistema. Agora, também

entendemos como essas solicitações fluem pelo seu sistema, o que é fundamental para a construção de sistemas mais escaláveis . Reconhecemos também as exigências específicas das aplicações web e móveis e a forma como estas interagem com o seu servidor. E nas próximas aulas, começaremos a analisar estratégias para otimizar e dimensionar essa configuração. Com o crescimento da nossa base de usuários, um único servidor não é suficiente para lidar com o aumento da demanda. E para acomodar mais usuários, podemos separar nossa camada web, que lida com o tráfego web e móvel, da camada de dados, que gerencia o banco de dados. Essa configuração nos permite dimensionar

cada servidor com base em sua carga específica. Mas, quando se trata de escolher o banco de dados certo, como saber qual banco de dados específico é o melhor para nossa aplicação em particular? Quando se trata de seleção de banco de dados , existem duas opções principais. A primeira opção são os bancos de dados relacionais ou SGBDs, que são estruturados em tabelas e linhas. Alguns exemplos populares são PostgreSQL, MySQL, banco de dados Oracle ou SQLite. Por outro lado, temos

bancos de dados não relacionais ou NoSQL. Essas soluções são adequadas para aplicações que exigem flexibilidade e acesso rápido a grandes volumes de dados não estruturados. Alguns exemplos são Cassandra, MongoDB, Redis ou Neo4j. Vamos começar explorando os bancos de dados relacionais. Esses bancos de dados utilizam a linguagem de consulta estruturada, ou SQL, para encontrar e manipular dados. Os dados

aqui estão estruturados em tabelas, que são os blocos de construção fundamentais dos bancos de dados SQL, e são semelhantes a planilhas. Cada tabela é composta por colunas, que podem ser consideradas os campos ou atributos da tabela. E também consiste em linhas, que são registros individuais dentro desta tabela. Por exemplo, se você imaginar uma tabela de clientes , dentro dessa tabela podemos ter colunas como ID, nome, idade e e-mail. E para cada linha, podemos ter clientes específicos, como o ID 123, o nome será John, a idade será 40, e assim por diante. Mas, quais são as

vantagens de usar um banco de dados SQL? Em primeiro lugar, eles suportam operações de junção complexas entre várias tabelas. Por exemplo, imagine que temos uma tabela de clientes e também uma tabela de produtos . E agora queremos criar uma tabela separada que conecte os clientes aos produtos que eles encomendaram. Com SQL, você pode unir essas duas tabelas em uma tabela de pedidos, que conterá as informações sobre os IDs dos clientes que fizeram o pedido, bem como os IDs dos produtos que esse cliente encomendou. E

esse processo de combinar duas ou mais tabelas em uma única tabela é chamado de operação de junção em SQL. Outra grande vantagem é que elas proporcionam consistência e integridade de dados robustas, especialmente para transações. Transações em SQL são uma sequência de uma ou mais operações SQL executadas como uma única unidade atômica, e cada transação em SQL segue o acrônimo ACID. Você pode pensar em um exemplo de transação como uma transferência bancária. Primeiramente, todas as transações são atômicas, o que significa que a transação inteira é tratada como uma única unidade, que ou é totalmente bem-sucedida ou totalmente falha.

Cada transação também é consistente, o que significa que ela transforma o banco de dados de um estado válido para outro estado válido. E também oferecem isolamento, o que significa que as modificações feitas por transações simultâneas são isoladas umas das outras e não interferem umas nas outras. E, por último, oferecem durabilidade, o que significa que mesmo se o sistema ou o servidor de banco de dados falhar, os dados permanecerão lá. E agora vamos dar uma olhada nos bancos de dados não relacionais. Bancos de dados não relacionais podem assumir diferentes formas. Por

exemplo, temos bancos de dados de documentos como o MongoDB, ou você pode usar bancos de dados de colunas largas como o Cassandra, bancos de dados de chave-valor como o Redis e bancos de dados de grafos como o Neo4j. Vamos analisar cada um desses tipos separadamente, começando pelos repositórios de documentos. O MongoDB é o exemplo mais popular de um banco de dados documental, e os dados são armazenados em documentos semelhantes a JSON , o que nos permite ter estruturas de dados complexas dentro de um único registro. Em seguida, temos os armazenamentos em colunas largas , onde os dados são armazenados em tabelas, linhas e colunas dinâmicas. Alguns exemplos disso são o Cassandra ou o Cosmos DB. A

principal vantagem desses bancos de dados é que eles podem lidar com escalas massivas e são muito bons para muitas operações de gravação. A outra opção são os bancos de dados de grafos, que se concentram em armazenar as entidades e seus relacionamentos como grafos. Um exemplo de banco de dados de grafos é o Neo4j. Por exemplo, na Amazon, eles usaram o banco de dados gráfico Neptune, que os ajuda a fazer recomendações de produtos com base em seus pedidos anteriores. E o outro tipo popular são os armazenamentos de chave-valor. Aqui, os dados são

armazenados em pares de chave-valor. A maior vantagem dos armazenamentos de valores chave é a sua simplicidade e rapidez. Como são armazenadas principalmente na memória RAM, a leitura e a gravação nesses bancos de dados são extremamente rápidas em comparação com outros bancos de dados. Alguns exemplos de armazenamentos de chave-valor são o Memcached ou o Redis. Então, esses são os quatro principais tipos de bancos de dados NoSQL. Agora vamos dar

uma olhada nas vantagens desses bancos de dados NoSQL. Se você observar o mesmo exemplo que usamos para os bancos de dados SQL, onde temos clientes e produtos, e queremos uni-los em pedidos. Por exemplo, no MongoDB, você poderia ter isso como um único documento, armazenando assim todos os dados do usuário, bem como os pedidos e produtos, em um único documento. E, devido a essa estrutura, os bancos de dados NoSQL conseguem lidar com conjuntos de dados altamente dinâmicos e extensos, sem a estrutura imposta pelos bancos de dados relacionais. Além disso, são otimizados para baixa latência e escalabilidade. Então,

quando você deve usar bancos de dados relacionais em vez de bancos de dados não relacionais? Aqui está uma breve comparação entre os dois. Se os dados da sua aplicação estiverem bem estruturados e com relações claras, então você deve usar bancos de dados SQL. Por exemplo, se você tem um aplicativo de comércio eletrônico que rastreia clientes e pedidos, esse é um bom caso de uso para um banco de dados SQL. Em seguida, se você precisar de forte consistência e integridade transacional. Por exemplo, se

você tiver um aplicativo financeiro ou um sistema bancário, deverá usar bancos de dados SQL. No entanto, se seu aplicativo exige latência extremamente baixa para respostas rápidas, então você deve optar por bancos de dados não relacionais. Ou, se os dados forem não estruturados ou semiestruturados, como objetos JSON, e os relacionamentos não forem tão cruciais, então você também deve optar por bancos de dados NoSQL. E, por último, se a sua aplicação exigir armazenamento flexível e escalável para volumes de dados massivos. Por exemplo, para um mecanismo de recomendação que armazena dados de atividade do usuário em formato de chave-valor, você também deve optar por bancos de dados NoSQL.

Vamos explorar as duas principais abordagens para o escalonamento, que são o escalonamento vertical e o escalonamento horizontal. E também veremos por que o escalonamento horizontal geralmente é mais adequado para aplicações com alto tráfego . Primeiro, temos a escala vertical, ou às vezes também chamada de ampliação de escala. Isso significa simplesmente que estamos adicionando mais recursos ao nosso servidor existente, ou seja, RAM, CPU ou quaisquer outros recursos que possam nos ajudar a lidar com mais tráfego. Essa abordagem é simples e funciona bem para aplicações com tráfego baixo ou moderado . No entanto, isso tem suas

limitações, que são, em primeiro lugar, as limitações de recursos. Existe um limite máximo para a quantidade de recursos que você pode adicionar a um único servidor e, eventualmente, você atingirá um limite para o quanto poderá atualizar seu novo servidor. E o segundo motivo é a falta de redundância, o que significa que se este servidor falhar, você não terá outros servidores para atender seus usuários, o que implica que toda a sua aplicação ficará inoperante com o seu único servidor. Por outro lado, temos o escalonamento horizontal, que também é chamado, às vezes, de escalonamento horizontal. No caso de escalonamento horizontal, estamos simplesmente adicionando mais servidores para compartilhar a carga. Assim, em vez de termos

um único servidor, poderíamos replicar e ter três servidores iguais. E agora podemos distribuir essa carga entre esses servidores em vez de lidar com todas elas em um único servidor. Em geral, essa opção é mais adequada para aplicações de grande escala , pois oferece maior tolerância a falhas. E uma maior tolerância a falhas significa que, se um de nossos servidores falhar, ainda teremos dois servidores disponíveis. Assim, esses dois servidores podem continuar atendendo nossos usuários enquanto o segundo servidor se recupera da falha.

Além disso, oferece melhor escalabilidade, pois você pode adicionar mais servidores conforme a necessidade. Em vez de três, você poderia introduzir uma quarta, que lidaria com o novo tráfego de entrada. Mas como implementamos o escalonamento horizontal? No caso de um único servidor, sabemos que todas as solicitações de nossos clientes foram direcionadas para esse único servidor, seja por meio do aplicativo móvel ou do computador. Mas e se agora tivermos três servidores para lidar com toda a carga? Como distribuímos as

solicitações dos clientes? Digamos que nosso aplicativo móvel faça uma solicitação. Como saber para onde devemos encaminhar essa solicitação? Deve ser enviado para o servidor um, para o servidor dois ou para o servidor três? E parece que precisamos de algo intermediário, que direcione o tráfego para os servidores apropriados. E essa parte no

meio é chamada de balanceador de carga. Utilizamos balanceadores de carga para distribuir o tráfego entre vários servidores. Por exemplo, aqui temos três servidores: o servidor um, o dois e o três. Sempre que recebemos uma nova solicitação dos clientes, o balanceador de carga decide onde há menos carga e redireciona o tráfego para esse servidor. Além disso, controla a tolerância a falhas, o que significa que, se um de nossos servidores falhar, como o servidor três, ele interromperá o envio de tráfego para o terceiro servidor, já que este não estará mais disponível, e enviará todo o tráfego para os servidores dois e um até que o servidor três esteja disponível novamente. Além disso, pode tornar nosso aplicativo mais

escalável, pois podemos adicionar um quarto servidor e quaisquer outros servidores que desejarmos, e esse balanceador de carga garantirá que todo o tráfego seja distribuído uniformemente. Portanto, essas são as duas principais abordagens de escalonamento: o escalonamento vertical e o escalonamento horizontal. No caso de escalonamento vertical, estamos simplesmente adicionando mais recursos ao mesmo servidor, mas no caso de escalonamento horizontal, estamos adicionando mais usuários à nossa base de servidores e, em seguida, usamos um balanceador de carga, que distribui o tráfego entre vários servidores. Mas, neste momento, esse balanceador de carga é uma espécie de caixa preta para nós, porque não entendemos como ele funciona. Como o sistema processa as solicitações? E como ele distribui o

tráfego? Então, vamos explorar isso na próxima lição e ver exatamente como isso funciona e quais são as estratégias que usamos no balanceamento de carga. Os balanceadores de carga distribuem o tráfego de entrada entre vários servidores, garantindo também que nenhum servidor individual fique sobrecarregado. Mas como isso realmente acontece? E como funciona a lógica de distribuição do tráfego de entrada? Para entender

melhor os balanceadores de carga, vamos explorar sete estratégias e algoritmos comumente usados ​​no balanceamento de carga. Vamos começar com o round robin, que é um dos algoritmos mais populares. Isso ocorre principalmente porque é a forma mais simples de balanceamento de carga, onde cada servidor no pool recebe uma solicitação em ordem sequencial rotativa, o que basicamente significa que a primeira solicitação recebida é direcionada ao primeiro servidor, a próxima solicitação vai para o segundo servidor e a terceira vai para o terceiro servidor. E quando o último servidor é alcançado, neste caso o servidor três, ele redireciona de volta para o primeiro servidor, e depois novamente para o segundo servidor, e assim por diante. Isso funciona bem para servidores com especificações semelhantes, ou seja, se todos os nossos três servidores tiverem a mesma capacidade, o round robin será uma boa opção . A

próxima opção é o algoritmo de conexões mínimas . Ele direciona o tráfego para o servidor com o menor número de conexões ativas. Por exemplo, se tivermos 10 conexões ativas no servidor um, teremos nove conexões ativas no servidor dois e 40 conexões ativas no servidor três. Se receber uma nova solicitação do cliente, irá encaminhá-la para o servidor dois, pois este possui o menor número de conexões ativas no momento. Assim, agora terá mais uma conexão. Isso

é particularmente útil para aplicações em que você tem sessões de duração variável, ou seja, uma sessão pode durar 10 minutos, outra 1 minuto e assim por diante. Nesse caso, o balanceador de carga levará isso em consideração e enviará o tráfego para o servidor com o menor número de conexões . A terceira opção é o menor tempo de resposta. Este algoritmo está mais focado na capacidade de resposta dos servidores. Digamos que nosso primeiro servidor seja altamente responsivo, o segundo tenha baixa responsividade e o terceiro tenha responsividade média.

Nesse caso, o balanceador de carga escolhe o servidor com o menor tempo de resposta e o menor número de conexões ativas, o que significa que primeiro ele tentará enviar o máximo de conexões possível para o servidor com maior capacidade de resposta, mas também leva em consideração as conexões ativas. Digamos que este servidor atinja 40 conexões ativas; então, ele mudará para o terceiro servidor, pois este é o servidor de resposta média, e enviará algum tráfego, digamos, outras 20 solicitações para o servidor de resposta média . Depois disso, ele passará para o segundo servidor e poderá enviar mais 10 solicitações para esse terceiro servidor até que as redirecione de volta para o primeiro servidor. Isso é eficaz quando o objetivo é fornecer o tempo de resposta mais rápido às solicitações e você também possui servidores diferentes com capacidades distintas. A quarta opção é o algoritmo de hash IP , que determina qual servidor receberá a solicitação com base no hash do endereço IP do cliente. Isso é

útil quando você deseja que seus clientes se conectem consistentemente ao mesmo servidor. Vamos supor que o cliente um faça uma solicitação ao seu balanceador de carga. O balanceador de carga usará o endereço IP do cliente e, com base nisso, fará um hash do endereço e o enviará para um servidor apropriado, digamos, o servidor dois. Todas as solicitações futuras do cliente um serão então encaminhadas para o balanceador de carga, que usará o mesmo algoritmo de hash de IP e, com base nesse endereço IP, redirecionará novamente as solicitações do usuário um para o servidor dois. Isso é útil se for importante para um cliente conectar-se consistentemente ao mesmo aplicativo.

Se cada um dos seus servidores tiver informações sobre os clientes conectados a ele, então o hash de IP é uma boa opção. Além disso, existem também algoritmos ponderados. Estas são variantes dos métodos acima que também podem ser ponderadas. Por exemplo, você pode ter um sistema de rodízio ponderado ou um sistema de conexões mínimas ponderadas . Neste caso, os servidores são atribuídos a pesos, normalmente com base em sua capacidade e métricas de desempenho.

Por exemplo, se o primeiro servidor tiver 16 GB de RAM, o segundo tiver 32 GB e o terceiro tiver 64 GB, com base na RAM do servidor e em outras métricas, eles recebem pesos, e o balanceador de carga leva isso em consideração ao redirecionar o tráfego. Primeiro, tentará enviar o máximo de conexões possível para o primeiro servidor, pois ele tem maior peso, o que significa que oferece melhor desempenho. Em seguida, tentará enviar o restante do tráfego para o segundo servidor e, por fim, a pequena porção restante irá para o primeiro servidor. Existem também algoritmos geográficos, que são algoritmos baseados em localização que direcionam as solicitações para o servidor geograficamente mais próximo do usuário. Digamos que este aplicativo seja para usuários dos EUA, então a maioria dos usuários se conecta a este aplicativo a partir dos EUA, mas também temos uma parte dos usuários que se conectam da Europa. E em nosso conjunto

de servidores, podemos ter um servidor localizado no leste dos EUA, outro no oeste dos EUA e o último em algum lugar da Europa para essa pequena base de usuários que estão localizados na Europa. Portanto, se um usuário vier da Europa e fizer uma solicitação a este balanceador de carga, ele será redirecionado para o servidor na Europa. Por outro lado, se um usuário vier dos EUA e fizer uma solicitação a este balanceador de carga, ele verificará a localização desse usuário americano com base em seu endereço IP e, em seguida, o redirecionará para o servidor do Leste ou do Oeste dos EUA. Esse tipo de balanceamento de carga é útil para serviços globais onde a redução da latência é importante. E o último tipo mais popular é o hash consistente.

Neste caso, utilizamos uma função hash para distribuir os dados entre vários nós. Temos uma função hash dentro de um balanceador de carga e, geralmente, imaginamos um espaço hash associado a ela, que forma um anel hash, como um círculo. Essa função hash forma um círculo onde temos os servidores, por exemplo, o servidor um, dois e três, que estão localizados na frente desse balanceador de carga. Assim, sempre que uma nova solicitação chega de um usuário, essa função hash pega o endereço IP desse usuário e, com base nisso , localiza esse usuário nesse anel hash. Digamos que ele localize o ponto em algum lugar aqui e, dependendo de qual servidor estiver mais próximo deste ponto, por exemplo, neste caso, este está mais próximo do servidor dois, ele redireciona o tráfego para esse servidor.

Essa é uma forma um pouco mais complexa de balanceamento de carga, mas também garante que o mesmo cliente se conecte consistentemente ao mesmo servidor, como no caso do hash de IP. Também comentamos que, sempre que um servidor fica inativo, esse balanceador de carga garante que o tráfego não seja redirecionado para esse servidor. Mas como é que o sistema sabe, em primeiro lugar, que este servidor não está disponível? Para isso, a maioria dos balanceadores de carga vem com recursos de verificação de integridade, o que significa que eles monitoram constantemente os servidores enviando solicitações de verificação de integridade para todos eles, e têm informações sobre quais servidores estão online, digamos que os três primeiros servidores estejam disponíveis, e quais estão offline, ou seja, o quarto servidor, que está offline. Assim, sempre que detecta uma falha na verificação de integridade, o sistema sabe que o quarto servidor não está mais disponível e, com base nessa informação, se a próxima solicitação vier do cliente, não a redirecionará para o quarto servidor até que a verificação de integridade seja bem-sucedida novamente e o sistema saiba que o quarto servidor está online de novo.

E agora, vejamos alguns exemplos de balanceadores de carga. O que são eles, afinal? Como podemos implementá-las? Em primeiro lugar, temos balanceadores de carga de software. Por exemplo, o Nginx é provavelmente o tipo mais comum de balanceador de carga de software.

Possui outras funcionalidades e também é usado como servidor web, mas oferece ainda a funcionalidade de balanceador de carga. Normalmente, você instala o Nginx no seu servidor e, em seguida, configura os servidores que devem ter a carga balanceada, bem como o algoritmo. E como você pode ver, também inclui exames de saúde, que eu mencionei. Assim, você pode configurar verificações de integridade entre seus servidores, e isso monitorará seus servidores constantemente, e sempre que um deles ficar inativo, o tráfego não será redirecionado para ele . Outro exemplo de balanceador de carga de software é o HAProxy, um software de código aberto que você pode instalar em seu servidor e configurar como desejar. Em seguida, temos o Citrix, que também oferece funcionalidade de balanceamento de carga e, novamente, este é um balanceador de carga de hardware . Portanto, você não precisa configurá-lo você mesmo. Outros exemplos semelhantes ao AWS são o balanceador de carga do Azure e o balanceamento de carga do Google Cloud. Agora, vamos falar sobre o conceito de ponto único de falha no projeto de sistemas. Essa é uma parte de todo o seu sistema que, sempre que falha, derruba todo o sistema junto.

Resumindo, trata-se de qualquer componente que possa causar a falha de todo o sistema quando para de funcionar. Por exemplo, imagine a seguinte configuração: os clientes se conectam ao nosso balanceador de carga, que os distribui para as APIs, e temos um único banco de dados usado por todos os servidores de API. Nesse caso, o banco de dados é um exemplo de ponto único de falha. Sempre que este banco de dados ficar indisponível, todas essas APIs não conseguirão se conectar a ele e, por causa disso, todas elas também não funcionarão corretamente, e nossos clientes não receberão nenhuma resposta dos servidores. Portanto, ter pontos únicos de falha em seu sistema é problemático porque eles podem criar vulnerabilidades.

A primeira desvantagem óbvia é a confiabilidade, pois uma única falha, como a falha deste banco de dados, pode derrubar todo o sistema, o que poderia significar prejuízos para a empresa, já que os usuários não conseguiriam acessar nossa plataforma. Talvez eles também não consigam acessar a página de finalização da compra ou outras partes do sistema, o que pode causar prejuízos ao negócio. Isso também representa um problema de escalabilidade, pois sistemas com pontos únicos de falha como esse geralmente têm dificuldades para escalar, já que cada componente aumenta o risco de falha dessa única parte. E a última parte também traz um problema de segurança, porque se você tiver um único ponto de falha em seu sistema, como o balanceador de carga, os invasores podem comprometer esse ponto enviando um grande volume de tráfego para ele e, se isso falhar, todo o sistema ficará inoperante. Falaremos sobre como evitar pontos únicos de falha no banco de dados na seção de bancos de dados, mas nesta seção, podemos analisar como evitar que os balanceadores de carga se tornem um ponto único de falha, pois, no momento, temos apenas um balanceador de carga configurado e, se esse balanceador de carga falhar, todos os nossos usuários não poderão acessar este ponto e também não poderão acessar nossas APIs.

A primeira estratégia é adicionar redundância ao nosso sistema. Isso significa que podemos usar mais de um balanceador de carga e, por exemplo, se o segundo balanceador de carga falhar, os usuários não poderão se conectar a ele. Nesse caso, podemos redirecionar todo o tráfego para o primeiro, que então distribuirá a carga entre os servidores. Monitoraremos a integridade do segundo balanceador de carga e, assim que ele voltar a ficar online e disponível, redirecionaremos 50% do tráfego para ele . Outra estratégia é usar verificações de integridade e monitoramento para os próprios balanceadores de carga . Como vimos, o balanceador de carga pode

realizar verificações de integridade nos servidores e verificar se eles estão online ou offline. Podemos usar a mesma estratégia para balanceadores de carga e verificar continuamente seu estado de funcionamento. Assim, sempre que um de nossos balanceadores de carga falhar, saberemos que não devemos redirecionar nenhum tráfego para ele até que volte a ficar online. E o terceiro tipo comum são os sistemas de autorrecuperação, o que significa que monitoramos a integridade do nosso balanceador de carga e, se em algum momento detectarmos que ele está inativo, o substituiremos por um novo balanceador de carga, que é basicamente uma instância do mesmo balanceador. Dessa forma, não causaremos interrupções e nossos clientes poderão se conectar a esse novo balanceador de carga.

Vamos começar por entender o que é uma API. API significa interface de programação de aplicativos, que define como os componentes de software devem interagir entre si.

Digamos que de um lado você tenha o cliente, que pode ser o celular ou o navegador do usuário, e do outro lado você tenha o servidor, que responderá às solicitações. Portanto, a API aqui é apenas um contrato que define esses termos, que são os tipos de solicitações que podem ser feitas. Assim, ela nos fornece uma interface sobre como fazer essas solicitações, ou seja, quais endpoints temos, quais métodos podemos usar e assim por diante. Além disso, quais respostas podemos esperar do servidor para um endpoint específico? Primeiramente, trata-se de um mecanismo de abstração, pois oculta os detalhes de implementação ao mesmo tempo que expõe a funcionalidade. Por exemplo, podemos

fazer uma solicitação para salvar os dados de um usuário neste servidor, mas não nos importamos com a lógica que funciona nos bastidores deste servidor. Nos interessa apenas a interface fornecida por meio desta API, utilizamos apenas esse endpoint e armazenamos o usuário sem sequer conhecer os detalhes de implementação. Além disso, define os limites do serviço, pois estabelece interfaces claras entre sistemas e componentes. Isso nos permite ter vários servidores. Podemos ter um servidor responsável pelo gerenciamento dos usuários. Podemos ter outra entidade

responsável por outros registros, digamos, para gerenciar as postagens e assim por diante. Isso permite que diferentes sistemas se comuniquem independentemente de sua implementação subjacente, como navegadores de clientes com servidores ou servidores com outros servidores e assim por diante. Agora, vamos nos concentrar nos estilos de API mais importantes que você encontrará durante a fase de projeto. São elas: RESTful, GraphQL e gRPC. O mais comum deles é o REST, que significa transferência de estado representacional. Esses

tipos de APIs utilizam uma abordagem baseada em recursos, usando os métodos HTTP como protocolo. Uma das vantagens das APIs REST é que elas são sem estado, o que significa que cada solicitação contém todas as informações necessárias para processá-la e não precisamos de nenhuma solicitação anterior para poder processar a solicitação atual. E utiliza os métodos padrão do protocolo HTTP, que são GET para buscar dados, POST para armazenar dados, [ __ ] ou PATCH para atualizar dados e DELETE para excluir dados. Assim, com base em suas características, o REST é mais comumente usado em aplicações web e móveis. Em seguida, temos o GraphQL, que é o segundo estilo de API mais comum depois das APIs REST. GraphQL

é uma linguagem de consulta que permite aos clientes solicitar exatamente o que precisam. Isso significa que ela possui um único ponto de extremidade para todas as operações e podemos escolher o que esperamos receber dessa API, fornecendo o payload na requisição. E as operações aqui são chamadas de consulta sempre que estamos recuperando dados ou mutação sempre que estamos atualizando dados, sendo o equivalente a [ __ ], PATCH ou POST nas APIs RESTful. Existe também uma assinatura para operações, que serve para comunicação em tempo real . A vantagem das APIs GraphQL é que elas permitem minimizar o número de requisições ao servidor. Digamos que precisamos de

alguns dados e que, em APIs RESTful, precisaremos fazer três requisições para obter todos esses dados. No caso do GraphQL, podemos fazer uma única requisição e obter todos esses dados, evitando as duas requisições desnecessárias que teríamos que fazer em uma abordagem RESTful. E por isso, esta é a opção recomendada para interfaces de usuário complexas, ou seja, sempre que você tiver interfaces de usuário complexas em que uma página possa precisar de dados diferentes e outra página possa precisar de outros dados complexos aninhados. Nesses casos, o GraphQL é a melhor escolha em comparação com as APIs RESTful. E a última opção é o gRPC. Eu diria que

este é o menos comum dentre esses três. gRPC é uma estrutura RPC de alto desempenho que utiliza buffers de protocolo para comunicação. Os métodos em gRPC são definidos como RPCs nos arquivos proto e suportam comunicação bidirecional e em fluxo contínuo. Essa é uma excelente abordagem, especialmente para microsserviços e comunicação interna do sistema, pois é mais eficiente quando se trabalha entre servidores em comparação com GraphQL ou APIs RESTful. A diferença entre APIs REST, GraphQL e gRPC é relativamente clara, mas vamos também esclarecer a diferença real entre APIs REST e GraphQL com exemplos.

Como você viu, o REST oferece endpoints baseados em recursos. Nesse caso, precisamos fazer três solicitações para obter todos esses dados. E utiliza métodos HTTP para definir operações. Como podem ver, estes são endpoints HTTP e estamos usando especificamente o método GET. E as estruturas de resposta são fixas, o que significa que, se você recebeu uma resposta para esse usuário específico, na próxima vez poderá esperar exatamente a mesma estrutura de resposta. Talvez alguns dados sejam modificados, mas a estrutura permanece sempre a mesma. Além disso,

oferece versionamento explícito, então, como você pode ver, vem com a versão V1 para a API V1, e posteriormente, se houver uma atualização importante, ela se tornará a versão V2 e assim por diante. Agora, se compararmos isso com as APIs GraphQL, elas vêm com um único endpoint para todas as operações, geralmente /graphql ou algum endpoint de API, que é comumente usado para todas as operações. Nesse caso, usaremos uma única solicitação para obter os dados precisos de que precisamos e utilizaremos a linguagem de consulta do GraphQL. Esta é a aparência da linguagem de consulta . Como podem ver, começamos com uma

Depois, precisamos do nome do usuário, das postagens e, em seguida, definimos o que mais precisarmos a partir das postagens. Talvez precisemos apenas do título e do conteúdo, nada mais. E também os seguidores e o que precisamos deles, talvez apenas os nomes.

Isso nos permite ser mais eficientes em nossas solicitações em comparação com APIs RESTful, onde precisaríamos fazer três solicitações para obter os mesmos dados. Isso significa que o cliente precisa especificar a estrutura da resposta e, nesse caso, a evolução do esquema ocorre sem versionamento. Como você viu, aqui está com V1, V2 e assim por diante. Por exemplo, você pode ter seguidores V2, que será o segundo tipo de esquema de seguidores. Mas você também pode optar por

Nesse caso, você pode aproveitar o cache em nível de aplicação em vez do cache HTTP. Agora vamos discutir os principais princípios de design que nos permitirão criar APIs consistentes, simples, seguras e também de alto desempenho. Em última análise, a melhor API é aquela que podemos usar sem sequer ler a documentação. Por exemplo, se você viu os endpoints anteriores nos usuários, você verá que temos {slash} usuários {slash} 123. E obviamente, estamos

Em primeiro lugar, uma boa API deve ser consistente, ou seja, deve usar nomes, maiúsculas e minúsculas e padrões consistentes. Por exemplo, se você usar camel case em um dos endpoints, digamos que você tenha detalhes do usuário e faça isso em camel case, mas em outro caso você faça com snake case como user {barra} details, isso não é comum e não é consistente. O segundo princípio fundamental é manter tudo muito simples e focar nos principais casos de uso e em um design intuitivo.

Portanto, você deve minimizar a complexidade e buscar designs que os desenvolvedores possam entender rapidamente, talvez até mesmo sem ler a documentação. E a simplicidade se resume a isto: a melhor API é aquela que os desenvolvedores conseguem usar sem nem mesmo ler a documentação. Em seguida, obviamente, precisa ser seguro, então é necessário ter algum tipo de autenticação e autorização entre os usuários. Além disso, se você tiver entradas, precisa garantir que elas sejam validadas e também aplicar limitação de taxa; essas são as coisas mais básicas que você precisa fazer para manter suas APIs seguras. E o último pilar é o desempenho, portanto, você deve projetar visando a eficiência com estratégias de cache adequadas e paginação. Se você tiver uma grande quantidade

de dados, digamos milhares de posts, você não vai querer recuperar todos eles sempre que alguém fizer uma solicitação para obter um post. Portanto, você deve sempre usar paginação com algum limite e deslocamento. Além disso, a carga útil, ou seja, os dados que você enviará de volta, deve ser minimizada. E também, sempre que possível, você deve reduzir as viagens de ida e volta. Portanto, se você tiver a oportunidade de enviar alguns dados pequenos junto com a solicitação de um dos endpoints, é melhor fazer isso se souber que irá utilizá-los, em vez de criar outro endpoint para fazer uma solicitação para obter os mesmos dados.

Por exemplo, os recursos do protocolo HTTP permitem diretamente as funcionalidades RESTful, portanto, faz mais sentido usar o HTTP juntamente com APIs RESTful, pois ele também fornece códigos de status, que são ótimos para serem usados ​​com operações de crowdsourcing que você terá em APIs RESTful. Por outro lado, os WebSockets, que são outro tipo de protocolo, permitem dados em tempo real e também APIs bidirecionais. Portanto, essas APIs podem ser usadas em conjunto com APIs em tempo real sempre que você precisar de um aplicativo de bate-papo ou de streaming de vídeo; esse é um bom caso de uso para APIs WebSocket. No caso de APIs GraphQL, você usará novamente o protocolo HTTP em vez de WebSockets ou gRPC. O

gRPC, por outro lado, pode ser usado em conjunto com microsserviços em sua arquitetura para torná-la mais rápida em comparação com o HTTP. Portanto, a sua escolha de protocolo afetará a estrutura da API, bem como o desempenho e as funcionalidades. Portanto, você deve escolher com base em suas limitações e pontos fortes, e naquela que fizer mais sentido para o tipo de API que você desenvolverá. Agora, vamos discutir o processo de design da API . Tudo começa com a compreensão dos requisitos, que consiste em identificar os principais casos de uso e histórias de usuário que você precisará desenvolver.

Além disso, é importante definir o escopo e os limites, pois se for uma API muito grande, provavelmente você não desenvolverá todos os recursos de uma só vez. Portanto, você deve delimitar o escopo para incluir alguns recursos específicos que serão desenvolvidos e também o que está fora do escopo por enquanto. Em seguida, você deve determinar os requisitos de desempenho e, especificamente no caso da sua API, quais serão os gargalos e onde você precisa garantir um bom desempenho. Além disso, você não deve negligenciar as restrições de segurança, portanto, deve implementar todos os recursos básicos, como autenticação, autorização, limitação de taxa e talvez outros recursos adicionais, dependendo da API que você desenvolver. Quando se trata de abordagens de design, existem algumas maneiras de proceder. A primeira é a abordagem de cima para baixo

, na qual você começa com requisitos e fluxos de trabalho de alto nível. Isso é mais comum em entrevistas onde eles te dão os requisitos sobre o que a API vai fazer e então você começa a definir quais serão os endpoints, quais serão as operações e assim por diante. Mas também existe a abordagem de baixo para cima , que consiste em, se você já possui modelos de dados e recursos existentes, projetar a API com base neles. Isso é mais comum quando você trabalha em uma empresa que já possui seus modelos de dados e recursos de APIs, então você deve levar isso em consideração ao projetar a API. Também temos a abordagem "contrato em primeiro lugar" , na qual você define o contrato da API antes da implementação, ou seja, como as requisições devem ser e como as respostas devem ser. E

isso se assemelha mais à abordagem de cima para baixo, sendo também comumente utilizada em entrevistas. Quando se trata de gerenciamento do ciclo de vida de APIs, tudo começa na fase de projeto, onde você cria o design da API, discute os requisitos e os resultados esperados . Só depois disso você poderá iniciar o desenvolvimento e, possivelmente, os testes locais da sua API. Depois disso, normalmente você implanta e monitora o sistema, realizando mais alguns testes, mas agora em ambiente de homologação ou em produção. Mas depois vem a fase de manutenção, e é por isso que é importante desenvolvê-lo mantendo a simplicidade , para que seja mais fácil para você ou para outros desenvolvedores darem manutenção no futuro.

E, por último, as APIs também passam por uma fase de descontinuação e desativação. Portanto, essa é também a fase de descontinuação da API V1. Portanto, o desenvolvimento de APIs não se limita à fase de desenvolvimento, como se poderia supor, e não se resume apenas à programação. Portanto, a parte mais importante é projetá-lo, mantê- lo em condições de funcionamento e, eventualmente, desativá-lo no final.

Os protocolos da camada de aplicação situam-se no topo da pilha de rede, construindo-se sobre protocolos como o TCP e o UDP, que estão na camada de transporte. Esses protocolos na camada de aplicação definem os formatos e estruturas das mensagens, bem como os padrões de solicitação-resposta , o gerenciamento das conexões e o tratamento de erros. Abaixo disso, temos muitas outras camadas, como a camada de rede, a camada de enlace de dados ou até mesmo as camadas físicas, mas ao construir APIs, estamos principalmente preocupados com os protocolos da camada de API, que são HTTP, HTTPS, WebSockets e assim por diante. O tipo de protocolo mais comum

e também a base das APIs da web é o HTTP, que significa Hypertext Transfer Protocol (Protocolo de Transferência de Hipertexto). Essa é a interação típica entre cliente e servidor quando eles estão interagindo via HTTP. Como você pode ver, o cliente sempre envia uma solicitação e define o método, que pode ser get, post ou outros métodos, e define o URL do recurso, que pode ser em {slash} API {slash} produtos. Digamos que eles estejam solicitando dados para esse ID específico do produto e também definam a versão do protocolo HTTP que estão usando. Eles também definem o host, que é o domínio do seu servidor onde as informações são acessadas, e geralmente também autenticam antes de acessar qualquer recurso, podendo ser um token de portador, autenticação básica, OAuth, etc. Assim, uma vez que a solicitação

é autenticada no servidor, ela recebe a resposta, que tem um formato semelhante, e é uma resposta HTTP. Assim, você obtém a versão HTTP, que é a mesma que você solicitou , e o código de status, que pode ser 200 se a requisição foi bem-sucedida, 400 se houve um erro no cliente, 500 se o erro ocorreu no servidor, e assim por diante. Você recebe o tipo de conteúdo, que geralmente pode ser JSON de aplicativo, mas também pode ser uma página da web estática ou algo diferente. Existem muitos outros cabeçalhos que você pode controlar, como o controle de cache, por exemplo, usando o cabeçalho de controle de cache ou outras propriedades. Mas esses são os principais aspectos que você notaria nos ciclos de requisição e resposta HTTP.

Agora, em relação aos métodos, você tem o ` get` para recuperar dados, o `post` para criar dados no servidor, o `put` ou ` patch` para atualizar dados parcial ou totalmente e o `delete` para remover dados do servidor. E quando se trata de códigos de status, que são recebidos pelo servidor, você tem a série 200, que são casos de sucesso. Você tem o código 300 para redirecionamento, o código 400 significa que o cliente cometeu um erro na solicitação, portanto, este é um problema do lado do cliente, ou o código 500, que significa que o servidor cometeu um erro, ou seja, ocorreu algum erro no servidor, o que significa que este é um problema no servidor. Esses são os cabeçalhos comuns, como o tipo de conteúdo, que geralmente é definido pelo servidor, mas também pelo cliente; a autorização para fazer uma solicitação e autorizar o servidor; os cabeçalhos Accept; o controle de cache; o agente do usuário; e existem outros cabeçalhos, mas esses são os mais comuns. Temos também o HTTPS, que é basicamente o mesmo protocolo HTTP, mas com algum tipo de criptografia TLS ou SSL, o que significa que nossos dados agora estão protegidos durante a transmissão quando fazemos solicitações. Assim, adiciona-se uma camada de segurança

por meio desses certificados TLS ou SSL e criptografia, protegendo os dados em trânsito. E as vantagens do HTTPS são óbvias: seus dados são criptografados durante a transmissão, garante a integridade dos dados, permite autenticar os usuários antes que forneçam quaisquer dados e também traz benefícios para o SEO. E você corre muitos riscos ao usar apenas HTTP sem nenhuma criptografia, portanto, o padrão ouro é sempre usar HTTPS em servidores. O próximo tipo de protocolos são os web sockets. Embora tenhamos o HTTP, que é muito bom em padrões de requisição e resposta, às vezes o HTTP tem limitações. Por

exemplo, digamos que você esteja coletando alguns dados. Vamos supor que seja um chat de usuário, então você tem o cliente e o servidor. Do lado do cliente, você tem o chat do usuário e, no servidor, as mensagens entre dois usuários. Quando um dos usuários envia uma mensagem para o outro, ele envia uma solicitação ao servidor para notificar que uma mensagem foi enviada e recebe uma resposta do servidor, que pode incluir as mensagens dos outros usuários, se houver. E então, da próxima vez, se você precisar saber se há novas mensagens, precisará fazer outra solicitação ao servidor e, talvez, não haja nenhuma mensagem nova, então você receberá uma resposta vazia, sem novos dados. Então, basicamente, foi

um ciclo de solicitação-resposta desnecessário. E você pode fazer a solicitação a partir de outro momento, digamos, a partir de 1 minuto, e receber uma resposta. Agora você tem algumas mensagens, mas também pode ficar vazio novamente. Portanto, esse método não é o ideal para comunicação em tempo real. Como você pode ver, isso resulta em maior latência, desperdício de largura de banda com solicitações vazias e também no uso de recursos do servidor sem a necessidade de fazer solicitações. E para esses

casos, temos os web sockets, que resolvem esse problema. Assim, em um WebSocket, geralmente ocorre um handshake na primeira requisição, e agora você tem uma comunicação bilateral entre o cliente e o servidor, o que significa que, uma vez feito o handshake , o servidor pode decidir independentemente enviar dados para o cliente. Digamos que agora você tenha duas novas mensagens no servidor. Assim, o servidor pode decidir enviar essas mensagens ao cliente sem que este as solicite. Mas o cliente ainda pode solicitar dados; portanto, se o cliente precisar de dados externos ou de mais dados do servidor, ele ainda poderá fazer solicitações, mas o servidor agora também é capaz de enviar dados ao cliente de forma independente.

Portanto, é isso que permite obter dados em tempo real com latência mínima. Assim que novos dados chegam ao servidor, ele os envia para o cliente, reduzindo também o uso de largura de banda ao permitir a comunicação bidirecional. No modelo cliente-servidor com HTTP, você faria, digamos, novas solicitações a cada 5 ou 10 segundos para verificar se há novos dados no servidor, mas neste cenário, você não faz mais nenhuma solicitação além da primeira. Agora, sempre que houver novos dados, o servidor os enviará, e quando não houver dados a serem solicitados, você não precisará fazer solicitações desnecessárias ao servidor. O próximo tipo de protocolo muito comum é o Advanced Message Queuing Protocol (AMQP), um protocolo de mensagens corporativo usado para enfileiramento de mensagens e garantia de entrega. Nesse cenário, geralmente

há o produtor, que pode ser um serviço web, um sistema de pagamento ou algo semelhante. E, por outro lado, temos o consumidor, que pode ser o processador dos pagamentos ou dos sistemas de notificação e coisas do gênero . Assim, o produtor publica mensagens no agente de mensagens, e é aqui que entra o Protocolo Avançado de Enfileiramento de Mensagens (AMCP) . Você tem filas no meio. Vamos supor que uma dessas filas seja para processamento de pedidos. Assim, sempre que um novo

pedido é feito, o produtor publica uma mensagem nessa fila. E então, sempre que esse consumidor estiver livre, ele poderá extrair mensagens dessa fila e começar a atualizar o inventário e os dados no banco de dados. Isso permite que o consumidor obtenha dados daqui somente quando houver capacidade disponível. E sempre que esse consumidor estiver ocupado com outras tarefas, ele deixa a mensagem na fila e, posteriormente, quando tiver capacidade livre, ele recuperará a mensagem e começará a atualizar os dados. E quando se trata de tipos de troca de mensagens, temos a troca direta um-para-um, a comunicação distribuída (fan-out) ou a comunicação baseada em tópicos, e exploraremos esses aspectos mais detalhadamente quando chegarmos à seção de filas de mensagens.

O outro tipo comum de protocolo é o gRPC, que funciona com buffers de protocolo. Trata-se de um framework RPC de alto desempenho, inventado pelo Google, que utiliza o HTTP/2 para transporte, ou seja, a segunda versão do HTTP. Isso significa que os clientes devem ser compatíveis com HTTP/2; caso contrário, esse protocolo não poderá ser usado entre o cliente e o servidor. Mas é por isso que ele é mais comumente usado entre servidores, então geralmente o cliente é outro servidor, e temos alguns outros microsserviços se comunicando entre si com essa estrutura gRPC. Ele utiliza principalmente buffers de protocolo e também possui recursos de streaming integrados, pois usa HTTP/2.

Esses são, portanto, os tipos mais comuns de protocolos de API. Existem muitos outros, mas geralmente em 90% dos casos, você verá apenas esses protocolos. E ao escolher a opção certa, você deve considerar principalmente os padrões de interação. Normalmente, por padrão, usa-se HTTP se for apenas um ciclo de solicitação e resposta, mas se você estiver criando algo como um chat em tempo real ou alguma comunicação em tempo real , então você precisaria usar WebSockets. A escolha também depende dos requisitos de desempenho. Portanto, se você

tiver vários servidores e microsserviços se comunicando entre si, e houver a oportunidade de usar o gRPC, por exemplo, você pode optar por ele para aumentar o desempenho e a velocidade da comunicação, mas isso também depende da compatibilidade com o cliente. Por exemplo, a maioria dos navegadores não suporta a versão mais recente do HTTP, e é por isso que o gRPC não é muito comum para comunicação entre navegador e servidor. Também depende do tamanho da carga útil, ou seja, do volume de dados e da codificação, das necessidades de segurança com base na autenticação, criptografia e assim por diante, e também da experiência do desenvolvedor, ou seja, das ferramentas e da documentação. E também se resume à experiência do desenvolvedor, porque você trabalhará principalmente com essa API, e ela precisa ter boa documentação e ferramentas para que você possa trabalhar plenamente com esse tipo de protocolo de API. Resumindo, exploramos o papel dos protocolos de aplicação na pilha de rede, o HTTP e o HTTPS, que são os tipos mais fundamentais de protocolos, os WebSockets para comunicação em tempo real , o AMQP ( Advanced Message Queuing Protocol), que permite comunicação assíncrona e a adição de filas de mensagens entre o consumidor e o produtor, e também o gRPC (Google Remote Procedure Call), cuja principal vantagem é ser um framework RPC de alto desempenho que utiliza o HTTP/2 para transporte.

Então, discutimos a camada de aplicação, que inclui esses protocolos que normalmente usamos para construir APIs, mas ainda não sabemos sobre a camada de transporte, que inclui o TCP e o UDP. Portanto, na próxima lição, discutiremos essa camada e entenderemos qual dessas camadas de transporte, TCP ou UDP, é a melhor escolha dependendo da API que estamos construindo. A maioria dos desenvolvedores trabalha com APIs, mas nunca pensa no que realmente está entregando esses pacotes, como por exemplo, como a solicitação é feita do cliente para o servidor e como essa solicitação trafega pela internet? É aí que entra a segunda camada no modelo OSI, que é a camada de transporte, que inclui o TCP e o UDP . Ambos são protocolos da camada de transporte , o que significa que gerenciam a forma como os dados se movem de uma máquina para outra na rede, mas fazem isso de maneiras muito diferentes. Nesta lição, aprenderemos

sobre esses protocolos da camada de transporte. Vamos começar com o TCP, que é a versão confiável, porém mais lenta. Em seguida, aprenderemos sobre o UDP, que, resumidamente, é uma versão mais rápida e menos confiável do TCP. Vamos comparar as duas e decidir qual escolher com base nos requisitos da API. Vamos começar com o TCP, que significa protocolo de controle de transmissão. Imagine que você está

enviando um pacote com recibo, código de rastreamento e também com assinatura obrigatória. Portanto, quando você envia alguns pacotes pela internet, geralmente não os envia todos de uma vez. Às vezes, os dados são maiores, digamos que estejam divididos em três partes, então você precisa enviá- los separadamente. O primeiro pedaço, o segundo pedaço e também o terceiro pedaço. Portanto, neste caso, o TCP garante a entrega de todos esses três blocos.

Se um desses pacotes for perdido ou chegar fora de ordem, o TCP o reenviará ou o reordenará. Também é baseado em conexão, o que significa que, antes de enviar quaisquer dados, realiza um handshake de três vias, que consiste em estabelecer a conexão entre o cliente e o servidor. Também encomenda estes pacotes. Digamos que o cliente receba primeiro o primeiro pacote , depois o terceiro pacote e, em seguida, o segundo pacote. Isso garante que a ordem seja alterada para primeiro, segundo e terceiro.

Isso, obviamente, aumenta a sobrecarga, mas garante que seja preciso e confiável. É por isso que APIs que envolvem pagamentos, autenticação ou dados do usuário sempre usam TCP. Por outro lado, temos o UDP, que significa protocolo de datagrama do usuário. É rápido e eficiente, mas a desvantagem é que não garante que todos os pacotes chegarão. Por exemplo, se você estiver enviando quatro pacotes do servidor para o cliente, um desses pacotes pode ser perdido e não será enviado ao cliente, e o UDP não garantirá que ele seja entregue eventualmente. Portanto,

não há garantia de entrega. Não há qualquer tipo de aperto de mãos, conexão ou rastreamento. Mas, devido a essas compensações, a transmissão é mais rápida e tem menos sobrecarga, pois não precisa garantir que todos os pacotes sejam entregues ou na ordem correta. Por exemplo, em videochamadas, o UDP pode ser o melhor protocolo porque, se alguma informação for cortada no meio da chamada, ou digamos que você esteja em uma chamada com alguém e a conexão de internet dessa pessoa fique lenta, você não precisa receber a conexão antiga ou os dados antigos do que foi dito, porque você está na chamada naquele momento. Assim, o UDP é a opção ideal para videochamadas, jogos online ou transmissões ao vivo, porque se um desses pacotes for perdido, não há problema e você não precisa reenviar o pacote. Você pode simplesmente prosseguir e enviar

os próximos pacotes. Assim se parece o handshake de três etapas no TCP. Como você pode ver, o primeiro passo é o cliente enviar uma solicitação ao servidor. Na segunda etapa, o servidor sincroniza e confirma a solicitação. E, no primeiro passo, o cliente reconhece o servidor. E

é aqui que a conexão entre o cliente e o servidor é estabelecida. E agora eles podem começar a enviar e receber dados usando esse protocolo TCP. Resumindo, o TCP é a versão mais segura e confiável do UDP, mas é mais lento. Por outro lado, o UDP é mais rápido e leve, mas apresenta riscos. Por exemplo, se um dos pacotes entre a origem e o destino for perdido, ele não será reenviado, portanto não há garantia de entrega. Por outro

lado, se no TCP um dos pacotes for perdido, após um certo tempo limite, o quarto pacote ainda será reenviado, garantindo assim que todos os dados sejam entregues, diferentemente do UDP, onde alguns dados podem ser perdidos, mas a transmissão continua. Ao escolher entre essas duas opções, estes são os principais pontos que você deve levar em consideração. Se você precisa que a conexão seja segura e confiável, então precisa usar o TCP. Ou, se você precisa que seja rápido, leve, mas alguma perda de dados seja aceitável, então você precisará usar UDP. Por exemplo, é ideal para usar o TCP em serviços bancários, e-mails, pagamentos e assim por diante.

Por outro lado, o UDP é usado principalmente em streaming de vídeo, streaming em geral, jogos e assim por diante. Esses são os principais aspectos que você precisa saber sobre as camadas de aplicação e de transporte, e essas são as únicas camadas que serão necessárias para a construção de APIs. Antes que um sistema possa autorizar ou restringir qualquer coisa, ele precisa primeiro saber a identidade do solicitante, seja um usuário acessando nosso serviço por meio de um navegador ou aplicativo móvel, ou um serviço de terceiros tentando acessar nosso sistema. Às vezes, chamam o OAuth2 de método de autenticação quando, na realidade, trata-se de uma estrutura de autorização. Eles confundem login único com métodos de autenticação quando, na verdade, trata-se de um padrão de experiência do usuário. Primeiro vamos entender o que é autenticação e depois abordaremos os diferentes métodos de autenticação. Assim, a autenticação responde a uma pergunta simples: quem é o usuário, quem quer que esteja tentando acessar nosso sistema. Digamos que você tenha um sistema como o seu gateway de API, a camada de APIs, a camada de serviços e também o armazenamento de dados. Antes que alguém possa fazer solicitações ao seu gateway de API e começar a acessar serviços e dados, essa pessoa precisa primeiro ser autenticada. É aí que eles enviam uma

solicitação de login. Isso pode vir de um usuário ou de outro serviço. É aqui que confirmamos a identidade do usuário, se for válida, e concedemos acesso ao nosso sistema, ao nosso gateway de API e a todos os outros serviços. Ou, se a identidade não for confirmada, rejeitamos a solicitação com uma resposta 401 (não autorizado). Este é o primeiro passo antes que eles tenham acesso à autorização, que define o que eles podem acessar e fazer depois de conseguirem entrar no seu sistema. Mas isso já é assunto para outra

discussão. Nesta aula, vamos nos concentrar principalmente na autenticação e nos diferentes métodos de autenticação que podemos usar para verificar a identidade do usuário. Agora vamos ver os diferentes métodos de autenticação que temos para verificar a identidade do solicitante, começando pelos métodos básicos. Esses são os conceitos básicos de autenticação, chaves de API e autenticação baseada em sessão . Vamos começar pelo primeiro item da lista, que é o fluxo de autenticação básica. Esta é a

forma mais simples de autenticação. Digamos que você esteja fazendo uma solicitação ao servidor para acessar algum recurso como API/users para recuperar os dados do usuário. Você receberá inicialmente uma resposta de acesso não autorizado porque não forneceu as credenciais. Assim, solicitamos ao usuário ou ao serviço que forneça credenciais antes de acessar qualquer recurso no servidor. Assim, na próxima solicitação ao mesmo recurso, eles também fornecem o cabeçalho de autorização, que contém a versão codificada em base64 do nome de usuário e da senha desse usuário.

É aqui que verificamos no lado do servidor. Se as credenciais forem válidas, respondemos com o status 200 OK, retornando os dados do usuário no corpo da requisição; caso contrário, autorizamos novamente o acesso, marcando as credenciais como inválidas. O problema com esse método é que o base64 é facilmente reversível, portanto, é um método inseguro, a menos que seja encapsulado com o protocolo HTTPS. E mesmo assim, raramente é usado hoje em dia em produção fora das ferramentas internas, porque você está enviando as credenciais com cada solicitação e está enviando a versão codificada em base64 , o que não é tão seguro. Por isso também temos uma autenticação digest, que é um pouco melhor e usa o algoritmo de hash MD5. Portanto, esse

método funciona de forma semelhante à autenticação com a versão básica. Então, digamos que você esteja tentando acessar o mesmo recurso que os usuários. A resposta inicial será 401 (não autorizado), solicitando que você insira as credenciais. Em seguida, você fará a mesma solicitação, mas com a resposta criptografada, que conterá o hash MD5 em vez da senha e do nome de usuário em texto simples. E o processo é o mesmo do anterior. Se as

credenciais forem inválidas, você receberá um erro 401 (não autorizado). Caso contrário, você receberá a resposta de sucesso com os dados do usuário no corpo da solicitação. Este método é ligeiramente melhor do que o básico, pois utiliza o algoritmo de hash MD5, mas ainda está desatualizado e raramente é usado hoje em dia, porque temos opções melhores, como você verá em breve. E se você está se perguntando como configuramos essas opções na autorização? Por exemplo, se você estiver fazendo a solicitação pelo Postman ou pelo código, deverá incluí-la como cabeçalho na solicitação. Aqui você pode definir o

tipo de autenticação e notará os recursos que estamos discutindo aqui, como a autenticação básica, que foi a primeira versão, ou a autenticação digest, que é a segunda versão, e verá os outros métodos disponíveis, incluindo a opção de chave de API . O Postman usa esses termos para todos esses tipos de autenticação, apenas para simplificar a interface, mas esse é também um dos motivos pelos quais os desenvolvedores se confundem e pensam que todos são tipos de autenticação, quando alguns são métodos de autenticação e outros são frameworks de autorização. Em seguida, temos a autenticação por chave de API. É aqui que você gera uma chave única para cada cliente, que então a envia com cada solicitação para acessar os recursos. Portanto, para a mesma solicitação que discutimos, ela chega primeiro ao seu servidor de API e incluirá o cabeçalho de autorização ou o X-API-Key, que conterá a chave de API que você gerou para o usuário. Normalmente, essas chaves de API

são armazenadas em um banco de dados juntamente com o hash da chave e os escopos associados a ela . Por exemplo, se você já tentou acessar APIs gerando uma chave no painel de controle e, em seguida, recebeu essa chave de volta, que você pode anexar às solicitações, é aí que você já usou a chave de API desse serviço para acessar os dados. Portanto, se você incluiu essa chave na solicitação, o servidor primeiro fará uma busca da chave de API na tabela de permissões ou usuários e, se conseguir verificar que a chave de API é válida, autorizará a solicitação e enviará a resposta bem-sucedida com os dados no corpo da resposta. Caso contrário, o usuário receberá uma resposta 401 (não autorizado). E se a chave estiver faltando, como no cabeçalho de autorização ou no X-API-Key, retornamos um erro 400 (solicitação inválida), pois a chave da API é necessária para acessar esse tipo de sistema.

Um problema com as chaves de API é que, se a chave vazar, qualquer pessoa poderá usá-la e começar a acessar os recursos em seu nome, e não há um prazo de expiração integrado, a menos que você o implemente por conta própria. Outro ponto é que isso pode parecer semelhante aos JSON Web Tokens, mas as chaves de API são apenas sequências aleatórias sem informações incorporadas, enquanto no JWT podemos armazenar informações, como você verá em breve. Portanto, o servidor aqui não tem como saber quem é o proprietário da chave ou quais permissões essa pessoa possui sem consultar o banco de dados. Em seguida, temos a abordagem tradicional da web , que é a autenticação baseada em sessão . É aqui que o usuário faz login com suas credenciais e, em seguida, criamos uma sessão em algum tipo de armazenamento de sessão. Esse armazenamento de sessão

pode ser tão simples quanto mantê-lo na memória, como uma variável, mas o problema é que o perderemos quando o servidor reiniciar ou falhar. Outra opção é usar ferramentas como o Redis, que é uma das mais comuns em produção por ser rápido e suportar o vencimento de sessões. Ou podemos usar um banco de dados dedicado, como um banco de dados do tipo SQL. Outra opção, embora muito rara, é usar o sistema de arquivos do servidor que você está utilizando. O problema com essa solução é que ela não é escalável e, no geral, o Redis costuma ser a escolha preferida para produção por ser rápido e ter expiração de chaves integrada. Assim, na

primeira requisição, estamos obtendo o ID da sessão e, em seguida, definindo o cookie de sessão no lado do cliente. Em seguida, para quaisquer outras solicitações futuras que contenham esse cookie, consultamos a sessão no armazenamento de sessão aqui e, se a sessão for válida, recuperamos os dados do usuário e os enviamos com a resposta autorizada. Caso contrário, se não for encontrada, se não conseguirmos localizar a sessão, então esse usuário não está autenticado, e enviamos a ele uma resposta de não autorizado. Um dos desafios da autenticação baseada em sessão é que ela mantém estado, o que significa que o servidor precisa se lembrar das sessões. Precisamos de algum tipo de armazenamento de sessão aqui. E

funciona muito bem para aplicativos web tradicionais, mas não escala tão facilmente para APIs ou sistemas distribuídos. Agora, vamos analisar a autenticação baseada em tokens. Vamos abordar a autenticação por portador, tokens JWT, tokens de acesso e de atualização, e como isso se compara à autenticação baseada em sessão . Em vez de sessões, as aplicações modernas geralmente usam tokens. Assim, o cliente envia um token com cada requisição. Por exemplo, temos um login

com credenciais onde o usuário incluirá suas credenciais no cabeçalho de autorização, que incluirá o tipo de autenticação, que é "bearer", e também o token, que validaremos no lado do servidor. Uma coisa que os desenvolvedores confundem aqui é o token de portador (bearer token) e os JSON Web Tokens. O token Bearer significa simplesmente que quem possui esse token tem acesso; portanto, é um padrão, mas não um método específico. E o tipo mais comum de token de portador é o JWT, JSON Web Token. Basicamente, é um objeto JSON assinado que contém o ID do usuário ou o e-mail para validarmos o usuário, além do tempo de expiração e outras informações que precisamos armazenar, como funções, permissões e assim por diante.

Então, o que fazemos no servidor de autenticação é validar as credenciais assim que recebemos o cabeçalho de autorização, e é um processo sem estado, o que significa que não precisamos de um banco de dados para consultar, e é por isso que também é escalável em comparação com a autenticação baseada em sessão . Antes da revolução do JWT, por exemplo , um token era apenas uma sequência de caracteres sem nenhuma informação. Esse token era enviado e, em seguida, consultado em algum tipo de banco de dados, e somente então podíamos verificar se o usuário tinha acesso. A desvantagem disso é que, obviamente, ainda mantém estado, pois precisamos do acesso ao banco de dados ou ao cache, o que é necessário sempre que o token é usado. Com os JSON Web Tokens, agora podemos codificar e verificar, por meio da assinatura, suas próprias declarações, e é isso que nos permite emitir tokens JWT de curta duração e sem estado, ou seja, autossuficientes e independentes de terceiros. Eles não precisam acessar

o banco de dados, o que reduz a carga sobre o banco e também simplifica o processo de autenticação para o servidor. Assim, na primeira vez receberemos as credenciais e validaremos o usuário e, se forem válidas, geraremos o JSON Web Token e o enviaremos ao cliente. A partir deste ponto, o cliente pode fazer solicitações e incluir este token de portador, que é o cabeçalho de autorização que contém a autenticação do portador com o token. E esse token, na maioria dos casos, é um JSON Web Token. Verificamos essa assinatura localmente, sem precisar acessar o banco de dados. E se o token for válido,

retornamos os dados solicitados. Caso contrário, retornaremos uma resposta não autorizada. Os sistemas modernos também utilizam dois tipos de tokens. Um deles é o token de acesso e o outro é o token de atualização. O motivo de precisarmos de dois tokens aqui é que os tokens de acesso têm curta duração e são usados ​​para chamadas de API ao servidor, enquanto os tokens de atualização têm longa duração e são usados ​​para obter novos tokens de acesso, basicamente para renovar o token de acesso.

Sempre que um usuário envia uma solicitação de login e efetua o acesso, ele recebe esses dois tokens. Geramos um token de acesso válido por 15 minutos a 1 hora e um token de atualização que pode durar dias ou até semanas. O cliente agora usará o token de acesso para acessar a API e fazer as solicitações, e o sistema também armazena os tokens de atualização. Um ponto importante a observar é que nunca armazenamos esses dados no armazenamento local, mas sim em cookies que só podem ser acessados ​​via HTTP. Isso nos impede de sofrer ataques XSS no lado do cliente.

E depois disso, o usuário permanecerá conectado sem precisar inserir as credenciais novamente. Se o token de acesso deles expirar, eles receberão uma resposta de não autorizado e é aí que usaremos o token de atualização, que armazenamos, para gerar um novo token de acesso no servidor externo. Podemos fazer uma solicitação com esse novo token e ela nos retornará os dados com sucesso, já que renovamos o token de acesso. OAuth 2 é um dos conceitos que muitas vezes é mal compreendido.

É uma estrutura de autorização e não de autenticação. Então, isso responde à pergunta: a que este aplicativo pode acessar em nome do usuário? Por exemplo, se você quiser conceder a um aplicativo acesso ao seu Google Drive para que ele possa ler seus arquivos de lá, normalmente você conectaria sua conta do Google Drive a esse aplicativo externo. E você está dando permissão ao aplicativo para acessar seus dados. O processo funciona da seguinte forma: primeiro, você será redirecionado para a tela de consentimento da autenticação OAuth do Google , onde será exibida a solicitação de permissão. E se você permitir

que este aplicativo leia os arquivos do Drive em seu nome, ele retornará o código de autorização para este aplicativo externo, ou pode ser o seu próprio aplicativo. E o processo funciona da seguinte forma: você troca o código pelo token e retorna o token de acesso do Google OAuth para poder ler os dados. Essa é a parte confusa, porque você está recebendo um token de acesso para a API do Google Drive e pode pensar que se trata de um método de autenticação, mas o token de acesso apenas comprova que o aplicativo pode acessar seus recursos. Mas isso não informa ao aplicativo quem você é. Isso apenas comprova que o aplicativo tem permissão para acessar determinados recursos do seu Google Drive. Assim, a partir deste ponto, o

aplicativo poderá solicitar arquivos com esse token e retornar os arquivos do usuário a partir da API do Google Drive. Em seguida, temos o OpenID Connect, que adiciona autenticação além do OAuth 2. Assim, quando você clicar em "Fazer login no Google", por exemplo, por meio do seu aplicativo, você será redirecionado para o endpoint de autorização. Isso mostrará a tela de login onde você concede acesso para entrar no Google por meio do seu aplicativo. Se você inserir suas credenciais e der seu consentimento, o provedor retornará o código de autorização. Após essa etapa, seu

aplicativo trocará o código por tokens e retornará o token de acesso em conjunto com o token de ID. A partir daqui, o token de acesso serve para autorização OAuth 2, mas o token de ID é um JSON Web Token que contém sua identidade, incluindo seu e-mail ou nome de usuário, e seu ID de usuário. Isso significa que, a partir deste ponto, seu aplicativo poderá verificar a assinatura e extrair a identidade do usuário para enviar o token de ID para verificação ao seu servidor. E, ao possuir esse token de identificação, seu aplicativo agora pode criar sua própria sessão e conceder o token de acesso para esse usuário. Esta é uma solução moderna. É seguro

e também escalável. E é por isso que a maioria dos aplicativos hoje em dia usa esse tipo de autenticação, como login com o Google, GitHub, Microsoft e assim por diante. E, por último, vamos abordar o login único e os protocolos de identidade. O login único é uma experiência do usuário, não um método de autenticação, o que significa que você pode fazer login uma única vez, mas acessar vários serviços. Por exemplo, quando você deseja fazer login no Google ou no Okta, digamos que você queira acessar seu Gmail, seu Google Drive, o YouTube ou o Google Agenda, você pode fazer isso fazendo login uma única vez no provedor de identidade. Digamos que, neste caso, pode ser o Google

se você quiser acessar esses serviços. E o login único utiliza protocolos de identidade subjacentes para validar essas sessões. Assim, depois de iniciar sessão com o provedor de identidade, digamos que seja o Google neste caso, a sua sessão global é armazenada num armazenamento de sessão. E então você recebe um cookie de autenticação única (SLO) do seu cliente para que ele possa acessar outros recursos. Então, digamos que você queira acessar o Gmail pela primeira vez.

Depois de fazer login e verificar a sessão, você poderá acessar o Gmail. E na próxima solicitação, se você precisar acessar o Google Drive , não precisará fazer login novamente, pois esses cookies e a sessão já estarão armazenados no armazenamento de sessão. Então, nós apenas verificamos sua sessão e, se ela for válida, você também terá acesso ao Google Drive. E o mesmo se aplica ao YouTube, ao Google Agenda e a outros serviços. Como mencionei, o login único utiliza protocolos de identidade subjacentes. E esses

protocolos são o SAML, que significa Security Assertion Markup Language (Linguagem de Marcação de Asserção de Segurança), ou o OpenID Connect. Ambos são protocolos de identidade, utilizados em conjunto com o login único (SSO). No caso do SAML, para acessar o aplicativo, você é redirecionado para a página de login, e é aí que usamos o SAML para autenticação. Essa é uma solução comum em sistemas empresariais e legados como o Salesforce, painéis de controle corporativos e assim por diante. É um protocolo baseado em XML. Assim, quando você tenta fazer

login, é redirecionado para a página de login e, em seguida, recebe a declaração SAML em formato XML. E depois disso, sua identidade é confirmada como usuário e você pode acessar o aplicativo de terceiros. O SAML ainda é amplamente utilizado, mas é uma versão mais antiga em comparação com o OpenID Connect. Portanto, a próxima opção é o OpenID Connect como protocolo de identidade. Digamos que você queira acessar um aplicativo, e neste caso seja o Gmail.

Você será redirecionado para a página de login para fornecer suas credenciais. Após fornecer suas credenciais, o usuário é autenticado e você recebe o token de identificação no formato JSON Web Token. E é isso que você usará para confirmar sua identidade no Gmail. É assim, por exemplo, que o Google funciona internamente, e é uma abordagem mais moderna em comparação com o SAML, mas ambos continuam sendo muito seguros e relevantes. Esses são os tipos mais comuns de autenticação, e esse é apenas o primeiro passo para acessar nosso sistema.

Depois de identificar o usuário por meio da autenticação, você também precisa saber o que ele pode fazer e quais permissões ele possui. A autenticação é apenas o primeiro passo para que os usuários possam acessar seu serviço. Isso indica quem é o usuário e se ele tem permissão para acessar o seu serviço. É nesse momento que eles enviam uma solicitação de login, e você confirma ou nega a identidade deles. Mas depois disso, você também tem a etapa de autorização, que informa exatamente a quais recursos esse usuário pode acessar. Basicamente, indica

o que eles podem fazer, o que o usuário pode fazer no seu sistema. E é isso que abordaremos no próximo vídeo. A autorização é a etapa que ocorre após a autenticação, quando alguém faz login em nosso sistema. Assim, uma vez que a solicitação de login é aprovada, o que significa que o sistema agora sabe quem é o usuário, o próximo passo é decidir o que ele pode fazer, que é a etapa de autorização. É necessário verificar a quais recursos ou ações o usuário tem permissão de acesso, bem como quais ações são negadas a esse usuário.

É assim que controlamos a segurança e a privacidade nos sistemas, e neste vídeo você aprenderá como os aplicativos e sistemas gerenciam permissões usando os três principais modelos de autorização. A primeira é o controle de acesso baseado em funções. Em seguida, temos o controle de acesso baseado em atributos. Além disso, a lista de controle de acesso é outra forma de gerenciar a autorização. Além disso, você aprenderá como tecnologias como OAuth 2 e JWTs nos ajudam a aplicar essas regras na prática. Portanto,

primeiro ocorre a autenticação, que nos informa quem é o usuário e se ele tem permissão para acessar nosso sistema. Mas na etapa seguinte, temos a autorização, que determina o que você pode realmente fazer como usuário neste sistema. Se tomarmos o GitHub como exemplo e o acesso a repositórios no GitHub, veremos que existem permissões diferentes para usuários diferentes. Por exemplo, o usuário A pode ter acesso somente para escrita, o que significa que ele só pode enviar código para este repositório. Por outro lado, podemos ter o usuário B, e aqui você pode conceder apenas acesso de leitura, o que significa que ele só pode ler este repositório, mas não pode enviar código para ele, nem criar solicitações de pull, e assim por diante.

Por outro lado, também podemos ter usuários administradores, que possuem controle total e podem gerenciar todas as configurações do repositório. Eles podem até decidir excluir este repositório, e assim por diante. Assim, você pode ver que diferentes usuários podem ter diferentes controles de acesso aos sistemas. Para gerenciar esses controles de acesso, temos modelos de autorização comuns . Então, o modelo que acabamos de analisar é o de autenticação baseado em funções , que atribui funções aos usuários, como administrador, editor, acesso somente leitura ou acesso somente gravação. E

essa é a abordagem mais comum entre esses modelos de autorização. Mas também temos o controle de acesso baseado em atributos, que se baseia nos atributos do usuário ou do recurso . Portanto, este método é mais flexível e mais complexo em comparação com a autenticação baseada em funções. Outra abordagem comum é utilizar listas de controle de acesso (ACLs), onde cada recurso possui sua própria lista de permissões. Assim, você pode atribuir listas de permissões a um recurso, e isso determinará a quais recursos você poderá acessar. Por exemplo, essa é uma

forma comum de gerenciar documentos do Google, e vamos analisá-la com mais detalhes agora. E cada um desses modelos tem suas vantagens e desvantagens. Portanto, isso depende dos requisitos específicos do sistema, mas sistemas reais frequentemente combinam vários modelos para obter uma configuração mais complexa e segura. Primeiramente, temos o controle de acesso baseado em funções, ou RBAC, como a sigla em inglês. Aqui, os usuários são atribuídos a funções e cada função possui um conjunto definido de permissões. Por exemplo, como você viu

no GitHub, existem administradores, e os administradores geralmente têm acesso total a todos os recursos. Assim, eles podem criar, ler ou atualizar recursos. Eles podem até mesmo excluir recursos e gerenciar outros usuários nas funções. E em seguida temos o editor, que geralmente tem um nível de privilégio um pouco inferior ao dos administradores. Assim, eles podem editar conteúdo, como criar, ler ou atualizar recursos, mas não podem excluir recursos nem gerenciar outros usuários.

E em seguida, você pode ter usuários visualizadores, que só podem ler os dados. Portanto, eles podem ler os recursos e o conteúdo, mas não podem atualizar nem criar nada no seu sistema. Este é o método mais comum em modelos de autorização e é usado em aplicativos que você utiliza diariamente, como os painéis do GitHub ou Stripe, ferramentas de CMS, ferramentas de gerenciamento de equipes e assim por diante. O próximo modelo é o controle de acesso baseado em atributos, ou ABAC, em resumo. Esse controle de acesso vai além das funções. Assim,

utiliza os atributos do usuário ou os atributos do recurso e as condições do ambiente para definir o acesso. Você pode ver aqui alguns exemplos de políticas. Digamos que você queira permitir o acesso somente se determinadas condições forem atendidas. Neste caso, sempre que o departamento do usuário for definido como RH, você pode combinar isso com várias outras condições, como sempre que o atributo de recurso for igual a interno, e assim por diante. E somente nesse caso você lhes concede acesso, seja para leitura ou para escrita. Portanto, isso também pode ser

combinado com a autorização baseada em funções . Mas, neste caso, você está verificando o modelo de usuário ou o modelo de recurso em seu banco de dados e, com base nos atributos, permite ou nega o acesso. Então, como você pode ver, aqui estamos verificando atributos do usuário, como departamento, idade ou qualquer outra coisa que você queira verificar. Em seguida, você também pode combiná-lo com atributos do recurso, como confidencialidade, proprietário do recurso ou classificação. E isso também pode ser combinado com fatores ambientais como horário do dia, localização, tipo de dispositivo e assim por diante. Como

você está combinando esses atributos para conceder ou restringir o acesso, isso é mais flexível do que a autorização baseada em funções , mas requer um bom gerenciamento de políticas e geralmente é mais complexo, podendo apresentar conflitos com o controle de acesso baseado em atributos. O terceiro tipo comum são as listas de controle de acesso. Em vez de fornecer acesso baseado em funções ou em atributos, você pode ter uma lista de controle de acesso para o recurso específico. Digamos que você tenha um recurso como um documento ou um arquivo JSON. Aqui você pode encontrar uma lista de permissões que define quais usuários podem acessar este documento. Por exemplo, a

usuária Alice tem apenas acesso de leitura, ou o usuário Bob tem acesso de leitura e gravação, e outro usuário não tem acesso a este documento. Como podem ver, estamos gerenciando duas coisas aqui. Em primeiro lugar, quais usuários têm permissão para acessar este documento e, em segundo lugar, quais são as suas permissões. Assim, cada usuário possui permissões diferentes para acessar este documento. As ACLs são altamente específicas e também centradas no usuário, o que significa que é difícil escalá-las bem em sistemas com milhões de usuários ou objetos, a menos que sejam gerenciadas com cuidado. Mas, por exemplo, o Google

Drive é um exemplo disso, onde você tem documentos como um Google Doc e depois compartilha esse Google Doc com seus colegas, certo? Então, você compartilha um documento com acesso somente leitura para alguém e depois compartilha este documento com outra pessoa, que agora também pode editar e adicionar comentários a este documento. Este é um exemplo de lista de controle de acesso (ACL), usada no Google Drive e no Google Docs. Isso oferece mais controle sobre recursos e documentos, mas também é mais difícil de escalar com milhões de usuários, embora seja possível, como você pode ver, já que o Google Drive usa isso para seus documentos, planilhas do Excel e assim por diante. Então, esses eram os modelos de controle de acesso , mas como os sistemas aplicam essas autorizações? É aqui que

entram em cena o OAuth 2 e o JWT, ou tokens de acesso. Primeiro temos o OAuth 2, que é a autorização delegada, um protocolo usado quando um serviço deseja acessar os recursos de outro serviço em nome de um usuário. Por exemplo, se você quiser permitir que um aplicativo de terceiros leia seus repositórios do GitHub. Digamos que você esteja implantando seu aplicativo no Vercel, então você precisa dar ao Vercel o controle do seu repositório no GitHub. Em vez de fornecer seu nome de usuário e senha para um aplicativo de terceiros, o que não será nada seguro, pois você não sabe o que eles podem fazer com seu nome de usuário e senha. Dessa forma, você estará dando a eles

controle total. Em vez disso, o GitHub fornece a eles o token que representa as permissões que você aprovou para uso. Então, você, como usuário, envia uma solicitação por meio do aplicativo de terceiros para solicitar acesso aos seus repositórios e, em seguida, o GitHub fornece o token de acesso, que você deve criar. Portanto, você também deve fornecer quais recursos, a quais repositórios esse aplicativo de terceiros pode acessar e o que ele pode fazer. Eles podem criar, ler, atualizar, excluir ou qualquer outra permissão que você definir? Em seguida, o GitHub

envia a eles o token, que contém as permissões que esse aplicativo de terceiros tem permissão para usar. E o OAuth 2 define o fluxo para emitir e validar esses tokens de forma segura. Portanto, você fornece a eles o token de acesso e não sua senha, o que representa as permissões que você aprovou pessoalmente. Portanto, pode ser a leitura de repositórios específicos ou também a criação e o envio de alterações para esses repositórios, mas não a exclusão deles . Em seguida, temos também a autorização baseada em tokens usando JWT ou tokens de portador e lógica de permissão.

Após a autenticação do usuário, a maioria dos sistemas utiliza um token, geralmente um token JWT ou um token de portador (bearer token), que contém informações como o ID do usuário, as funções (como administrador ou editor) , os escopos de acesso (a quais áreas o usuário tem permissão para acessar), a data de expiração do token e quem o emitiu . Assim, sempre que um usuário faz uma solicitação, ela sempre carrega essas informações de token e chega ao servidor de backend. É aqui que o servidor verificará seu token e sua validade e aplicará a lógica de permissão apropriada . Portanto, para não confundir isso com modelos de autorização, existe uma distinção fundamental. O token geralmente contém a identidade e as informações do seu usuário, como você pode ver aqui. Mas os

modelos de autorização, como os baseados em funções ou em atributos, definem o que um usuário tem permissão para acessar. Portanto, os tokens são apenas mecanismos, enquanto estes são modelos de autorização. Resumindo, a autorização não se limita a permitir o acesso de usuários como a autenticação, mas também controla o que eles podem acessar depois de entrarem. Aprendemos o que é autorização e quais são os três modelos de autorização mais comuns: baseado em funções, baseado em atributos e lista de controle de acesso. E você também viu alguns exemplos práticos, como a forma como o GitHub gerencia seus tokens de autorização. Isso deve

lhe dar uma ideia de quando usar cada modelo, com base no sistema que você está construindo. E você também viu alguns padrões de implementação com OAuth 2 ou tokens JWT. Cada um desses modelos tem suas próprias vantagens e desvantagens, e os sistemas reais geralmente combinam vários modelos para se manterem flexíveis e seguros. APIs são como portas de entrada para o seu sistema. Se você os deixar desprotegidos, invasores e qualquer pessoa poderão entrar e fazer o que quiserem com os dados do usuário e com todo o sistema. Por isso,

no vídeo de hoje, vamos analisar sete técnicas comprovadas que ajudarão você a proteger suas APIs contra ataques indesejados. O primeiro item da lista é a limitação de taxa, que controla quantas solicitações um cliente pode fazer em um determinado período. Por exemplo, você pode definir um limite para o usuário A fazer, digamos, 100 solicitações por período de tempo à sua API. E se eles ultrapassarem esse limite e, digamos, fizerem 101 solicitações, você bloqueia a próxima solicitação e permite que algum tempo passe antes que eles possam enviar a próxima solicitação. Se você não configurar isso na sua API, os invasores poderão sobrecarregar seu sistema. Eles podem enviar milhares de

solicitações por minuto e sobrecarregar sua API, o que pode derrubar seu sistema, ou podem também usar força bruta para acessar seus dados. E esses limites de taxa podem ser definidos por ponto de extremidade. Por exemplo, digamos que você tenha um endpoint de comentários (barra) e que nele eles possam enviar uma solicitação para criar um comentário ou buscar comentários. Você pode definir esse limite para o nível do ponto de extremidade. Assim, este endpoint de comentários será configurado para um número estrito de solicitações por minuto. Você

também pode configurar isso por usuário ou endereço IP. Digamos que em A temos o endereço IP do primeiro usuário, em B o do segundo, em C o deste, e que o atacante possui um endereço IP correspondente a D. Se você receber a 101ª requisição do endereço IP D, saberá que esse usuário utilizou a API em excesso . Portanto, você irá bloqueá-lo no nível do endereço IP do usuário. Além disso, existe uma limitação geral de taxa para proteção contra ataques DDoS. Como é

possível definir o limite de taxa para funcionar por usuário ou por endereço IP, isso significa que esse atacante sozinho não pode enviar tantas solicitações. Você poderá bloquear isso com a limitação de taxa na sua API. Mas o que eles podem fazer é criar alguns bots e cada bot terá seu próprio limite, certo? Digamos que você tenha configurado para 100 por endereço IP. Portanto, cada um desses bots tem 100 e, no total, eles têm mais do que você permitiria ou do que seu sistema poderia suportar. É por isso que também existe a

limitação de taxa geral, que pode ser um número maior. Assim, sempre que todo o tráfego que chega ao seu servidor atingir ou ultrapassar esse número, você bloqueará temporariamente todas as solicitações até descobrir a causa raiz. E, claro, esses números são apenas exemplos. Na realidade, são muito mais de 1.000, mas isso é apenas um exemplo. O segundo item

da lista é "course", que significa compartilhamento de recursos entre origens diferentes. Isso controla qual domínio pode chamar sua API a partir de um navegador e, sem um curso adequado, sites maliciosos poderiam enganar os navegadores dos usuários para que fizessem solicitações em seu nome. Por exemplo, se sua API se destina apenas a atender seu aplicativo front-end, que está em app.yourdomain.com, então somente as solicitações dessa origem devem ser permitidas. Se alguém

lhe enviar uma solicitação como app.anotherdomain.com, você deverá bloquear essa solicitação e não permitir que essa pessoa use sua API para autenticação ou para acessar quaisquer dados dela. A terceira também é comum: injeções de SQL e não de SQL. Ataques de injeção podem ocorrer quando a entrada do usuário é incluída diretamente na consulta ao banco de dados . Por exemplo, um atacante pode modificá-

lo e enviar algumas consultas para ler ou excluir seus dados. Aqui, por exemplo, esta parte ignora completamente as verificações e, em seguida, o invasor pode usar essa consulta para começar a ler dados do seu banco de dados, modificar qualquer coisa ou até mesmo excluir todos os dados, todos os dados do usuário e quaisquer outras tabelas que você tenha neste banco de dados. Para resolver isso, sempre usamos consultas parametrizadas ou proteções de ORM. A próxima técnica a ser utilizada são os firewalls. Um firewall atua como um guardião, filtrando o tráfego malicioso do tráfego normal. Normalmente, essa conexão fica

entre a sua API e o tráfego de entrada. Por exemplo, se você usar o firewall de aplicativos da Web da AWS, ele poderá bloquear solicitações com padrões de ataque desconhecidos, como palavras-chave SQL suspeitas ou métodos HTTP estranhos. Isso significa que ele bloqueará quaisquer solicitações suspeitas de invasores, mas permitirá que outros ignorem a solicitação e acessem sua API. Algumas APIs também são privadas e só devem ser acessadas a partir de redes específicas. É por isso que também temos as VPNs, que significa redes virtuais privadas. As

APIs que estão dentro da rede VPN só podem ser acessadas por alguém que também esteja dentro dessa mesma rede, o que significa que algumas APIs são públicas, permitindo quaisquer solicitações da internet feitas por seus usuários. Mas estes, por exemplo, podem estar dentro da rede VPN, o que significa que se um usuário da web tentar acessar sua API, essa solicitação será bloqueada porque o usuário não está na mesma rede. Por outro lado, se você tiver outro usuário aqui que esteja dentro da rede VPN, ele poderá fazer uma solicitação a essas APIs e, nesse caso, contornará as verificações e sua solicitação chegará às suas APIs. Isso é útil quando você tem ferramentas internas. Vamos supor que você tenha um painel de administração interno e que a API desse painel só possa ser acessada por funcionários conectados à VPN da empresa.

Em seguida, temos o CSRF, que significa falsificação de solicitação entre sites. Isso engana o navegador de um usuário conectado, fazendo com que ele envie solicitações indesejadas à API. Vamos supor que você, como usuário, esteja conectado ao sistema do seu banco e que esse sistema utilize cookies para autenticação. Se o sistema bancário não for seguro e utilizar apenas cookies de sessão, outro site malicioso poderá usar seu cookie e enviar uma solicitação oculta de transferência de dinheiro por meio dele. Para evitar esses ataques, as empresas também usam tokens CSRF em combinação com cookies de sessão. Assim,

o sistema bancário verificará se o cookie de sessão está presente, mas também verificará se o token CSRF corresponde ao que eles possuem. E se não funcionar, bloqueará essa solicitação da outra fonte desconhecida, enquanto permitirá solicitações em seu nome. E o último que temos é o XSS, também chamado de cross-site scripting. Isso permite que invasores injetem scripts em páginas da web exibidas para outros usuários. Por exemplo, se você tiver uma seção de comentários e esse comentário for enviado para sua API, a API também o armazenará em um banco de dados. Você pode receber solicitações normais,

como "bela imagem" ou algo semelhante, e isso chegará à sua API. Sua API irá armazená-lo no banco de dados. Então está tudo bem por lá. Mas e se um atacante inserir um script nessa seção de comentários e, dentro desse script, tentar fazer várias coisas diferentes? Por exemplo, eles podem tentar obter o cookie de outro usuário ou podem tentar injetar algo em seu banco de dados.

E se você permitir isso, os dados chegarão ao seu servidor e serão gravados no banco de dados. Posteriormente, quando os outros usuários carregarem esta seção de comentários em suas telas, eles também receberão o comentário injetado diretamente em suas páginas da web, e o navegador executará esse código JavaScript malicioso no navegador dos outros usuários.
