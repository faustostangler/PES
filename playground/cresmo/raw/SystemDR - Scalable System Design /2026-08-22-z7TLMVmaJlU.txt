So, what does shipping even mean when the artifact [music] isn't a web service, but a pipeline? This is the single mental model I want you to leave with today. Traditional software CI/CD ships [music] one thing, code. A change gets built, unit tested, packaged into a deployable artifact, [music] and it starts serving traffic. Success is binary and immediate.

>> [music] >> The service is either up and healthy or it isn't. Data pipeline CI/CD ships three things at once. Code, yes, >> [music] >> but also the shape of the DAG or asset graph, and the schema of the data it reads and writes. All three have to be validated together [music] before anything reaches a scheduler. Testing has to happen against data [music] that actually looks like production, not just synthetic fixtures, because most pipeline bugs are data shape bugs.

>> [music] >> Nulls, type drift, unexpected cardinality that a plain unit test won't catch. And deployment doesn't target a fleet of servers. It [music] targets an orchestrator. Rollout has to be backfill aware, because if a [music] broken version ran for 6 hours before anyone rolled it back, the fix isn't [music] just deploy the old code. It's deploy the old code and reprocess the window [music] that ran wrong.

Here's the line I want you to remember. A pipeline deploy that [music] succeeds can still be wrong. Correctness depends on the shape of the data, not just the shape of the code. Keep that in mind because everything else in this talk is really just tooling built to make that distinction visible before it costs you anything.
