Let's talk about where this space is heading because I think there's a real architectural shift underway, >> [music] >> not just a checklist of best practices. An Airflow task in the classic model is fundamentally ephemeral. [music] It's a step that ran and once it's done, the orchestrator doesn't retain a durable [music] notion of say this table as a first-class object with its own identity and history. Dagster's software-defined asset model flips [music] that. The asset, a table, a file, a model, is the first-class object [music] and the code that produces it is secondary. And that identity is exactly

the hook that lets tooling do things an imperative task [music] graph structurally can't. Diff the lineage graph between two versions of code and say precisely which downstream tables are affected by a change. Attach a schema [music] directly to the asset definition and validate it in CI. Generate a genuinely useful preview environment [music] because the tool knows which specific assets changed, not just which files changed. You can see this playing out in three concrete [music] trends. Data contracts

becoming CI gates instead of Slack alerts after the fact, >> [music] >> lineage-aware diffing replacing manual code review guesswork, and quality checks that block a merge instead of triggering a 2:00 a.m. page [music] after the bad data has already shipped. To be clear, this doesn't mean imperative DAG frameworks are going away. Airflow [music] remains extremely well suited to complex operational schedules.

But even Airflow native shops are increasingly layering asset-aware features on top of task DAGs specifically to borrow this identity model.
