Let's look at a simplified, [music] but realistic slice of that pool-based harvester in code. This coroutine harvests [music] one table's metadata. It acquires a connection from an async pool, queries the schema catalog and an approximate row count, >> [music] >> builds a normalized metadata asset keyed by a stable URN, a unique resource name like [music] URN:catalog:postgres:prod.orders, >> [music] >> and upserts it into the catalog through the metadata API from the last slide. Three details matter here for production correctness.

>> [music] >> First, the retry decorator with exponential backoff. At scale, a harvester touching tens of thousands of tables will hit [music] connection resets and timeouts constantly. And without backoff, a blip turns into a thundering [music] herd retry storm against the source database. Second, everything runs through pooled non-blocking [music] connections because a synchronous harvester crawling one table at a time simply cannot keep pace with a warehouse adding hundreds of tables a week. >> [music] >> And third, the most important detail for correctness, upsert is idempotent. URNs

are deterministic, so rerunning the same harvest on a schedule updates the existing graph node instead of [music] creating a duplicate. Teams that skip idempotent URNs learn the hard way when a scheduler retries duplicates half the catalog overnight. URN design is worth getting right before the first production [music] run, not after.
