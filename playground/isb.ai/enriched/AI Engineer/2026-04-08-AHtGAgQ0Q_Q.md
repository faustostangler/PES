# Arquiteturas de Isolamento para Código Gerado por Inteligência Artificial

## A Realidade do Código Gerado por IA e o Modelo de Ameaças

O avanço das ferramentas de Inteligência Artificial redefiniu a velocidade do desenvolvimento de software, permitindo a transição do autocompletar de linhas para a geração autônoma de módulos inteiros. Contudo, ao conceder permissão para que agentes de IA escrevam e executem código em servidores e ambientes de produção, introduz-se um risco de segurança crítico: na prática, o código gerado por um modelo de linguagem (LLM) deve ser tratado com o mesmo nível de desconfiança aplicado a um script anônimo baixado da internet.

Como funções estatísticas de predição de texto, os modelos de linguagem não possuem discernimento sobre a segurança das instruções que produzem. Essa vulnerabilidade manifesta-se em três cenários de ameaça principais:

1. **LLM Alucinatório**: Falhas não maliciosas decorrentes de erros de interpretação do modelo. A IA gera rotinas com laços infinitos, recursões sem caso base ou importações de bibliotecas inexistentes, provocando esgotamento de memória e negação de serviço (_Denial of Service_).
2. **LLM Excessivamente Prestativo**: A tentativa do modelo de resolver uma tarefa varrendo as variáveis de ambiente em busca de credenciais. Ao tentar configurar uma conexão, a IA lê e expõe chaves de API e senhas de banco de dados que não deveriam estar acessíveis ao código gerado.
3. **Prompts Comprometidos**: Ataques por injeção direta ou indireta de prompt. Na injeção indireta, o modelo lê um documento ou página web externa contendo instruções maliciosas ocultas, convertendo o agente de IA em vetor de exfiltração de dados confidenciais.

Como o código gerado pela IA é executado com os mesmos privilégios do aplicativo hospedeiro, uma falha nesse nível concede à execução não confiável acesso irrestrito ao sistema de arquivos, à rede e às credenciais do servidor.

## O Princípio da Segurança Baseada em Capacidades

Para neutralizar os riscos da execução não confiável, a arquitetura de software deve afastar-se de estratégias defensivas baseadas em listas de bloqueio (_blacklists_). Tentar enumerar todas as chamadas de sistema, APIs ou padrões de código perigosos é uma abordagem falha, pois a omissão de uma única ameaça compromete todo o sistema.

A solução madura fundamenta-se no princípio da **Segurança Baseada em Capacidades** (_Capability-Based Security_), estruturada sob a política de negação padrão (_default-deny_).

> "Não enumere o que deve ser bloqueado; enumere estritamente o que é permitido."

Sob o paradigma de capacidades, o código em execução é privado de qualquer acesso por padrão. O ambiente concede explicitamente apenas as permissões mínimas e específicas necessárias para a execução da tarefa. Trata-se da mesma filosofia aplicada pelos navegadores modernos (nos quais uma aba não pode ler os dados de outra) e pelos sistemas operacionais móveis (onde o acesso à câmera ou ao microfone exige concessão explícita de permissão pelo usuário).

## O Espectro de Isolação: Isolados V8 versus Contêineres Linux

O isolamento de código gerado por IA varia em uma escala de complexidade e controle, sendo a escolha determinada pelos requisitos do caso de uso:

- **Isolados V8** (_V8 Isolates_): Ambientes de execução de altíssima velocidade baseados no motor do Google Chrome. Inicializam em frações de milissegundo e executam JavaScript, TypeScript e WebAssembly. Por design, não possuem modelo de processo, sistema de arquivos ou acesso à rede, constituindo um ambiente restrito ideal para execução de funções curtas, interpretadores de código e chamadas de ferramentas.
- **Contêineres Linux**: Ambientes virtuais completos com sistema operacional Linux, sistema de arquivos real, gerenciadores de pacotes (`npm`, `pip`) e gerenciamento de processos. Exigem alguns segundos para inicialização e maior alocação de memória, sendo necessários quando o código gerado precisa compilar aplicações, clonar repositórios Git ou rodar servidores de desenvolvimento de longa duração.

## Arquiteturas Práticas em Produção: Do Cloudflare Workers ao Prompt Motion

A aplicação prática desse espectro de isolamento é ilustrada em duas soluções de produção desenvolvidas sobre a infraestrutura da **Cloudflare**:

Na primeira abordagem — voltada à criação de habilidades dinâmicas para agentes —, utiliza-se a API de **Isolados V8** do Cloudflare Workers. Ao configurar a propriedade `globalOutbound = null`, o ambiente bloqueia integralmente qualquer solicitação de rede de saída. O código gerado pela IA é executado em um contexto sem sistema de arquivos, recebendo via RPC apenas vinculações (_bindings_) explícitas para operações restritas de banco de dados e registros de log.

Na segunda abordagem — exemplificada pela plataforma **Prompt Motion** (aplicação que gera e renderiza vídeos em código a partir de descrições em linguagem natural) —, a necessidade de executar compiladores e servidores de pré-visualização exige o uso de **Contêineres Linux** orquestrados por **Durable Objects**. Nessa arquitetura, estabelece-se o isolamento absoluto por usuário: cada cliente opera em um contêiner exclusivo, com sistema de arquivos próprio, impedindo que o código de um usuário acesse os dados ou processos de outro inquilino (_tenant_).

## O Padrão Proxy de Segredos e a Lista de Verificação Universal

Um dos erros recorrentes em arquiteturas de IA é injetar chaves de API privadas diretamente como variáveis de ambiente no contêiner de testes (_sandbox_). Caso o contêiner seja comprometido por uma injeção de prompt, as credenciais serão lidas e exfiltradas.

Para contornar esse risco, aplica-se o **Padrão Proxy de Segredos** (_Secret Proxy Pattern_). O contêiner de testes nunca recebe a chave de API real; em seu lugar, envia as solicitações externas para um endpoint intermediário mantido pelo servidor hospedeiro. O servidor valida a requisição, anexa os cabeçalhos de autenticação com a chave privada, executa a chamada ao serviço externo e retorna apenas a resposta sanitizada ao contêiner.

Para consolidar a segurança no processamento de código gerado por IA, a engenharia de software deve aplicar uma lista de verificação universal composta por oito diretrizes:

1. **Bloqueio de Rede por Padrão**: Desativar acessos de saída a menos que estritamente necessários.
2. **Concessão de Capacidades Mínimas**: Oferecer apenas APIs explicitamente autorizadas.
3. **Isolamento por Usuário**: Garantir contêineres e sistemas de arquivos dedicados por inquilino.
4. **Limites Rígidos de Recursos**: Definir *timeouts* de CPU e teto de memória para conter laços infinitos.
5. **Segredos Fora do Sandbox**: Utilizar proxies autenticados para operações sensíveis.
6. **Destruição Obrigatória**: Encerrar contêineres ociosos em blocos `try-finally`.
7. **Auditoria e Logs**: Registrar a autoria, horário e escopo de cada execução.
8. **Validação de Entrada**: Filtrar a sintaxe e o tamanho das instruções antes da execução.

## Expansão do Conhecimento

O isolamento por contêineres leves no contexto de Inteligência Artificial é frequentemente implementado através de **MicroVMs**, com destaque para a tecnologia **Firecracker** desenvolvida pela Amazon Web Services (AWS). O Firecracker permite criar máquinas virtuais minimalistas em milissegundos sobre o hipervisor KVM do Linux, combinando a velocidade de inicialização dos contêineres com a segurança de isolamento no nível de hardware oferecida pelas VMs tradicionais.

No campo da segurança em linguagem de programação, a especificação **WebAssembly** (WASM) estabelece um modelo de execução em ambiente isolado (_sandboxed_) por padrão. O código compilado em WASM opera em uma memória linear separada do processo hospedeiro e não pode realizar chamadas ao sistema operacional sem que funções importadas sejam explicitamente fornecidas pelo ambiente de execução (via especificação WASI).
