  Neste vídeo eu mostro a anatomia completa de uma skill, crio duas skills espelhadas (audit-md e audit-html) que fazem a mesma análise mas em formatos diferentes, rodo as duas no mesmo mini-projeto Node.js, e comparo o resultado: tokens, tamanho, utilidade real. No fim entrego os 2 arquivos prontos pra você baixar e adaptar pro seu fluxo.
  
  Se você usa Claude Code todo dia e ainda não montou uma skill própria, esse vídeo é pra você. A sacada das skills é que elas resolvem o problema de "todo dia eu colo o mesmo prompt longo" criando um arquivo versionado que o Claude carrega sob demanda. Cada skill é só uma pasta com um arquivo SKILL.md dentro. Sem framework, sem código, sem dependência.
  
  A anatomia é simples. Skills ficam em ~/.claude/skills/, cada uma é uma pasta com nome próprio e dentro tem um único arquivo SKILL.md. Esse arquivo tem 2 partes: frontmatter YAML no topo (com name e description) e corpo em markdown abaixo. O description é o gatilho, é onde você fala QUANDO o Claude deve ativar a skill. O corpo é o manual: fluxo de execução, template de output, princípios. Description ativa, corpo executa.
  
  Pra demonstrar com prova prática, eu criei duas skills que fazem a mesma coisa: audit completo de um projeto Node.js. A audit-md gera relatório em markdown estruturado. A audit-html gera o MESMO relatório, mas em HTML self-contained com dashboard escuro, cards de stats, árvore SVG do projeto, tabela de deps e cards coloridos de issues. Mesma análise, mesma informação, formato diferente.
  
  O alvo das duas é o mesmo mini-projeto: um todo-cli em Node.js com package.json com deps antigas, README incompleto, lib com tratamento de erro fraco e tests com cobertura ralinha. Os problemas estão lá de propósito, pra ver se as skills detectam.
  
  Rodo a audit-md primeiro. Comando simples: faça um audit do projeto, use a skill audit-md. O Claude ativa a skill via description, executa o fluxo do corpo, e cospe um audit-report.md com estrutura clara, tabelas e recomendações numeradas. Resultado: cerca de 470 tokens gerados, 2.7 KB de arquivo, 62 linhas. Lê em VSCode, terminal, GitHub. Vai pro git sem fricção.
  
  Em seguida rodo a audit-html com o MESMO prompt, só trocando o nome da skill. O resultado visualmente impressiona: abre no browser e tem dashboard completo, cards bonitos, SVG da estrutura. Mas tem custo: cerca de 1430 tokens gerados (3 vezes mais), 11.9 KB de arquivo (4.4 vezes mais), 240 linhas. E quando você usa fora do browser, vira fricção pura. Cat no terminal ilegível. Grep poluído com tags HTML. Git diff impossível de revisar. Editar manualmente é dor.
  
  A parte mais importante vem no fim, que é entender QUANDO usar cada formato. Markdown ganha como default pra audits que vão pro repositório, descrições de PR, RFCs, relatórios técnicos que outro dev vai editar, docs que entram no Notion ou Confluence. HTML self-contained tem nicho real pra apresentação pra cliente, B-roll de vídeo, dashboard one-off, screenshot pra post de blog, relatório executivo pra reunião pontual. Não é tudo ou nada, cada formato tem seu lugar.
  
  O veredicto: markdown não morreu. Continua ganhando como default porque é mínimo, portátil, diff-friendly. HTML self-contained tem nicho onde brilha, mas trocar o default do workflow custa 3 vezes mais tokens pra mesma informação útil.
